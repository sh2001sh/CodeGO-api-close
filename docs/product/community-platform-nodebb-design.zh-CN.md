# CodeGo 社区平台与 NodeBB 独立部署设计

> 状态：阶段 1 身份闭环及阶段 3 首批只读接口已完成代码实现和本地验证，待生产部署  
> 主站域名：`https://codegoai.com`  
> 社区域名：`https://community.codegoai.com`  
> 更新日期：2026-09-19

## 0. 实施状态

截至 2026-09-18，阶段 1 已在本地完成：`new-api` 已实现 OIDC Provider，NodeBB 已通过独立的 `nodebb-plugin-codego-oidc` 接入，主站登录与注册流程能够保留授权返回地址。NodeBB 核心未 fork，社区继续独立部署。

本地已经验证授权码流程、PKCE S256、RS256 ID Token、JWKS、一次性授权码、访问令牌、禁用账号拒绝、回调地址校验，以及 NodeBB 的真实登录重定向。论坛本地注册已关闭，论坛注册入口统一进入 CodeGo 注册，因此两端创建的账号都归属 CodeGo，同一个账号可以登录两个站点。

生产环境尚未部署。上线前仍需生成生产 RSA 签名密钥、在两台服务器配置相同的 OIDC Client Secret、执行主站数据库迁移并部署 `new-api`，随后构建和部署社区镜像。

当前尚未实现签名 Webhook 和后台会话撤销。CodeGo 禁用用户后，该用户不能发起新的 OIDC 登录、换取令牌或访问 `userinfo`，但已经存在的 NodeBB Session 不会立即失效；即时撤销现有社区会话属于后续生产加固项。

## 1. 结论

社区采用 **NodeBB 内容内核 + CodeGo 自定义主题和插件 + 独立服务器**。`new-api` 继续负责账号、渠道市场和所有业务事实，NodeBB 只负责社区内容与互动。

两套系统共享登录身份和渠道关联，但不共享数据库、Redis、Session、Cookie、文件目录或部署流程。社区故障不能影响 API 调用、充值、渠道路由、结算和控制台。

### 1.1 现在不要 fork NodeBB 核心仓库

第一步应创建自己的 `codego-community` 仓库，而不是 fork `NodeBB/NodeBB`：

- 使用官方 NodeBB 镜像或固定版本源码作为运行时。
- 自定义界面放入 `nodebb-theme-codego`。
- OIDC、渠道关联和外链治理放入独立插件。
- Docker Compose、Nginx、备份和升级配置放在自己的仓库。
- 记录 NodeBB 固定版本，并在测试环境验证后升级。

只有同时满足以下条件时才维护 NodeBB fork：

1. 需求无法通过公开插件 API、主题模板、Hooks 或上游配置实现。
2. 已验证核心补丁确实必要。
3. 已向上游提交或评估补丁，但短期不能合并。
4. 团队能够持续跟进 NodeBB 安全更新并重放补丁。

直接 fork 会把社区升级、安全补丁和冲突处理变成长期成本，目前没有这个必要。

## 2. 产品目标

社区解决四个问题：

1. 用户难以判断和选择渠道。
2. 渠道主只能在群聊中发布状态、维护和优惠信息。
3. 用户的问题反馈缺少公开进度和处理闭环。
4. 群聊广告不可控，需要允许站内渠道推广并禁止站外引流。

最终产品是以 AI 模型、工具、项目和技术实践为主体的社区。渠道主页、服务反馈与受控站内推广是利用 CodeGo 现有业务事实形成的特色能力，但不主导全站内容排序、成员等级和社区叙事。

## 3. 系统边界

```text
                           Cloudflare
                    /                       \
          codegoai.com             community.codegoai.com
                |                           |
        new-api 独立服务器             社区独立服务器
        Go + React                     Nginx + NodeBB
        主业务 PostgreSQL              社区 PostgreSQL
        主业务 Redis                   社区 Redis
                |                           |
                +---- OIDC / 签名 API -----+
                +------ 签名 Webhook ------+
```

### 3.1 `new-api` 负责

- 注册、登录、密码、账号状态和封禁。
- OIDC 身份提供方。
- 社区准入资格和渠道主资格。
- 渠道、分组、模型、倍率、检测和排名。
- API 调用记录、消费、账本和结算。
- 渠道主公开主页和渠道业务详情页。
- 用户是否真实使用过某个渠道的权威判断。
- 渠道和账号状态变化的 Webhook Outbox。

### 3.2 NodeBB 负责

- 帖子、回复、引用、表态、收藏和关注。
- 渠道公告、问题反馈、站内优惠活动和普通讨论。
- 举报、审核、禁言、社区封禁和申诉。
- 公开讨论、灌水区、举报与审核；首期关闭私信和实时聊天。
- 社区搜索与社区通知。
- 社区附件元数据；文件本体存储在 Cloudflare R2 或 S3。

### 3.3 禁止的耦合

- NodeBB 不读取 `new-api` 数据库。
- `new-api` 不读取 NodeBB 数据库。
- 不共享 Redis、Session Cookie 或用户密码。
- 不使用 iframe 嵌入社区。
- 不由主站反向代理整个 NodeBB 页面。
- 不在社区复制结算、请求日志或 API 密钥等敏感业务数据。

## 5. 主站前端改造

现有公开导航调整为：

```text
首页 | 市场 | 社区 | 模型 | 状态 | 控制台
```

“社区”是外部一级入口，跳转到 `community.codegoai.com`。跳转参数只能包含经过白名单校验的目标路径，不能携带访问令牌。

### 5.1 市场首页 `/market`

保留渠道选择、指标比较和路由池管理，渠道条目新增：

- 渠道主名称和认证标记。
- 渠道主主页入口。
- 最近一条渠道公告。
- 未解决反馈数量。
- “查看讨论”和“提交反馈”入口。
- 近 24 小时成功率、TTFT、请求量、倍率和数据更新时间。

社区热度不进入市场质量排名，防止刷帖影响渠道排序。

### 5.2 渠道详情 `/market/:groupSlug`

页面按以下顺序展示：

1. 渠道名称、在线状态、倍率和检测结果。
2. 支持模型与实时价格。
3. 成功率、TTFT、请求量和独立消费者数。
4. 最近维护记录和倍率变更。
5. 渠道主公开信息。
6. 最近公告和反馈统计。
7. 绑定 API Token、加入路由池等业务操作。
8. 跳转社区查看完整讨论或提交反馈。

### 5.3 渠道主主页 `/seller/:sellerSlug`

渠道主主页类似店铺主页，展示：

- 公开昵称、头像、简介、认证状态和加入时间。
- 旗下已发布渠道。
- 每个渠道的状态、倍率和主要模型。
- 累计请求量、真实消费者数和近 30 天质量摘要。
- 反馈解决率和首次响应时间。
- 最近公告与当前站内活动。

不得公开邮箱、数据库用户 ID、真实身份资料、API 密钥或消费者信息。

### 5.4 渠道主工作台

现有渠道主界面增加：

- 店铺资料。
- 社区公告。
- 待处理反馈。
- 站内优惠活动。
- 社区违规和申诉提醒。

工作台只展示待办摘要与数量，编辑公告、处理反馈和社区审核跳转到社区。主站不承担 NodeBB 内容编辑器和实时通知连接。

### 5.5 社区资源

现有“社区资源”审核与奖励功能首期继续留在主站，社区“资源”入口链接至现有页面。待社区运行稳定后，再决定是否迁移展示层；奖励发放和业务审核仍归 `new-api`。

## 6. 社区信息架构

社区首页采用跨板块广场 Feed，分类目录不是首屏，但成员可以进入板块视图并关注或忽略板块。

一级导航：

```text
最新 | 热门 | 关注 | 板块
```

- **最新**：跨全部未忽略板块的近期主题。
- **热门**：NodeBB 原生热门排序。
- **关注**：登录成员跟踪的内容。
- **板块**：技术、模型、工具、项目、资源、渠道和社区七个一级板块。

渠道板块承载渠道公告、讨论、反馈与站内活动；渠道主主页按渠道主聚合主站已验证的公开渠道。广场仍然混合展示各板块内容，渠道内容不获得额外排序权重。

### 6.1 视觉方向

- 与主站共用 Code Go 标识、基础蓝色和暖橙色经济强调色。
- 首页以帖子流和真实内容为主，只保留克制的广场导览。
- 渠道主主页显示主站实时核验的身份、渠道状态与详情入口。
- 支持快捷表态、引用回复、关注和实时通知。
- 成长与头衔来自社区贡献，不与消费金额、充值或渠道热度绑定。
- 社区主题只控制表现，业务权限必须由服务端插件校验。

## 7. 内容模型

普通主题只要求标题、正文和板块，回复不要求选择“方案、复现、证据、异议、追问、更新”等类型。社区不以格式限制正常表达；需要强业务约束的渠道公告、正式反馈和站内活动，在对应功能上线时通过独立入口与服务端字段实现，不改变普通发帖体验。

### 7.1 渠道公告（后续）

公告类型包括临时故障、计划维护、模型上下线、倍率调整、服务恢复和一般通知。渠道归属由 `new-api` 实时验证，不能使用 NodeBB 用户组代替所有权检查。

### 7.2 问题反馈（后续）

反馈类型包括无法调用、响应速度、模型不符、计费疑问、内容拦截和其他问题。用户必须在限定时间窗口内真实使用过对应渠道；校验依据为主站请求审计或结算记录。

反馈状态变化需要保留操作者、时间和原因。反馈用户、对应渠道主、版主和管理员拥有不同的状态变更权限。

### 7.3 站内优惠活动（后续）

渠道主只能从本人已审核渠道中选择推广对象，活动链接由系统生成并指向 `codegoai.com/market/...`。倍率、渠道状态和价格从主站读取，不能由发帖人自由声明。

活动必须设置起止时间，到期自动归档；同一渠道限制发布频率。

### 7.4 渠道与帖子关系（后续）

不为每个渠道创建 NodeBB 分类。帖子保存经过服务端验证的 `channel_id` 或 `group_id`，社区渠道页按关联 ID 聚合内容。这样渠道数量增长时不会形成大量空版块。

## 8. 账号共享与权限

`codegoai.com` 作为 OIDC Provider，NodeBB 作为 OIDC Client。

```text
访问社区
  -> 跳转 codegoai.com 授权
  -> 主站完成登录或复用已有会话
  -> 一次性授权码返回社区
  -> NodeBB 换取身份并建立独立社区 Session
```

建议 Claims：

| Claim | 含义 |
|---|---|
| `sub` | 用户稳定的 `ExternalId` |
| `name` | 公开昵称 |
| `picture` | 头像地址 |
| `account_status` | 账号是否可用 |
| `community_level` | 社区准入等级 |
| `channel_owner` | 是否至少拥有一个已审核渠道 |
| `role` | 普通用户、版主或管理员 |

NodeBB 不保存主站密码。昵称和头像只是社区副本，`sub` 不因改名而变化。

### 8.1 准入等级

1. **访客**：读取公开内容。
2. **已注册成员**：通过 CodeGo OIDC 登录后按板块权限发帖和回复；冷启动期不设邀请码或成功调用门槛。
3. **贡献者 / 核心成员 / 共建者**：依据持续的内容和社区贡献人工授予，后续再定义自动规则。
4. **认证渠道主**：主站至少有一个公开、审核通过的活跃渠道；该身份不提高帖子权重。
5. **板块主理人 / 管理员**：执行内容治理，但不能查看 API 密钥、Prompt、Response 或消费者隐私。

目标方案中，账号封禁、渠道主资格撤销和渠道下架通过签名 Webhook 同步。当前阶段尚未实现该 Webhook；涉及渠道权限的写操作在后续阶段实现时，仍须在发布时向主站校验，主站不可用时失败关闭，不根据旧缓存放行。

## 9. 广告与外链治理

允许的广告只有结构化的站内渠道活动。禁止：

- 站外 API 中转站。
- QQ 群、微信群、Telegram 群等联系方式引流。
- 短链接、二维码、IP 地址链接和混淆域名。
- 用户签名、头像和个人资料广告；私信功能首期关闭。
- 通过外部图片或附件绕过链接规则。

首期服务端策略覆盖主题标题以及帖子创建、编辑时的源正文，拦截高置信度群聊邀请、商业短链、联系方式和站外渠道导流，同时允许普通技术链接与代码示例。用户资料、图片与附件绕过、频率治理及更完整的域名信誉属于后续加固范围，不宣称当前规则已经覆盖所有广告形式。

首期白名单建议包括：

- `codegoai.com` 及受控子域名。
- GitHub。
- 官方模型厂商文档。
- 经管理员明确批准的开发文档站点。

代码块中的 URL 可以保留为不可点击文本。

## 10. 跨服务器接口

已实现以下服务端接口，供 NodeBB 使用：

```text
GET /api/community/v1/sellers?page=1&page_size=20&keyword=&provider=&sort=rating
GET /api/community/v1/members/:sub
GET /api/community/v1/members/:sub/channels?page=1&page_size=20&keyword=&sort=rating&viewer_sub=
PUT /api/community/v1/channels/:id/rating
```

请求必须携带独立服务凭据：

```http
Authorization: Bearer <CODEGO_COMMUNITY_API_SECRET>
```

该密钥只允许进入 `new-api` 和 NodeBB 的服务端环境变量，不能写入主题、浏览器脚本、公开配置或日志。它必须独立生成且不少于 32 个字符，不能复用 `OIDC_CLIENT_SECRET`、用户 API Key 或管理员令牌。

渠道馆列表按渠道主分页，只返回账号启用且至少拥有一个公开、验证通过并处于 `active` 或 `degraded` 状态渠道的用户；每个渠道主携带最多 3 条渠道预览。`keyword` 同时匹配公开用户名、显示名、渠道名称和渠道 slug；`provider` 保留为兼容参数，社区首期界面不展示类型筛选。渠道主排序支持 `rating`、`recent`、`channels`。成员接口返回 `sub`、`active`、公开用户名、公开显示名、`verified_channel_owner` 以及渠道主加权评分。渠道列表只返回该用户旗下公开、验证通过且状态可用的渠道，并支持渠道名称搜索以及 `rating`、`recent`、`name` 排序；列表接口支持 `page` 与 `page_size`，每页最多 50 条。

星级评分是独立于“通过 / 存疑 / 不通过”渠道反馈的社区评价：1 至 5 星分别映射为 2、4、6、8、10 分。同一 CodeGo 用户对同一渠道只保留一条当前评分，再次提交会更新原评分。渠道主不能评价自己的渠道。渠道主评分按各渠道的有效评分数量加权，等价于汇总其全部公开渠道的用户评分后计算平均值；没有评分时返回 `average_score=0`、`rating_count=0`，界面展示“暂无评分”而不是 0 分。

接口不会返回邮箱、数据库用户 ID、余额、倍率、收益、请求记录、内部渠道 ID、凭据尾号、API 密钥或加密凭据。未知账号返回 404；非法 `sub` 或分页返回 400；禁用账号查询渠道返回 403；未配置服务密钥返回 503；认证失败返回 401。数据库或依赖异常返回通用 500，详细错误只进入服务端日志。

首期星级评分只要求统一账号登录并禁止自评，尚未增加“真实消费者”门槛；后续若需要提高评分可信度，应基于主站调用记录增加已消费权重或准入条件，不能由 NodeBB 浏览器自行声明消费资格。

后续主站可向社区发送的事件：

- 用户封禁或恢复。
- 渠道主认证通过或撤销。
- 渠道审核通过、暂停、恢复或下架。
- 渠道公开名称变更。

安全要求：

- 独立客户端凭据和最小权限。
- HTTPS、请求签名、时间戳和随机数防重放。
- Webhook 事件 ID 幂等。
- 短超时、有限重试和死信记录。
- 密钥只进入环境变量或密钥服务。
- 社区无权调用主站管理员接口。

## 11. 社区部署

### 11.1 服务器建议

正式环境建议从以下配置启动：

- 4 核 CPU。
- 8 GB 内存。
- 80 GB 以上 SSD。
- 附件使用 R2/S3。
- PostgreSQL 每日备份，保留 7 至 14 天。

2 核 4 GB 可用于测试环境，不建议作为长期生产配置。NodeBB、PostgreSQL、Redis、搜索重建和备份同时运行时余量有限。

### 11.2 容器组成

```text
community-nginx
community-nodebb
community-postgres
community-redis
community-backup
```

生产镜像必须固定具体版本或 digest，不使用浮动 `latest`。升级流程为：备份数据库，在测试环境升级并验证插件，再滚动到生产。

### 11.3 独立仓库结构

```text
codego-community/
├─ compose/
│  ├─ docker-compose.yml
│  └─ docker-compose.production.yml
├─ nginx/
├─ themes/
│  └─ nodebb-theme-codego/
├─ plugins/
│  ├─ nodebb-plugin-codego-oidc/
│  ├─ nodebb-plugin-codego-channel/
│  └─ nodebb-plugin-codego-link-policy/
├─ scripts/
│  ├─ backup/
│  └─ upgrade/
├─ env.example
└─ README.md
```

NodeBB 版本锁定、主题、插件、部署和升级记录都进入此仓库；真实 `.env`、数据库备份和对象存储密钥不得提交。

## 12. 从现在开始怎么做

### 阶段 0：建立独立工程，不 fork 核心

1. 创建空的私有仓库 `codego-community`。
2. 写入 Compose、Nginx、`env.example` 和备份脚本骨架。
3. 选择并固定一个当前受支持的 NodeBB 稳定版本。
4. 在本地或测试服务器启动 NodeBB、PostgreSQL 和 Redis。
5. 配置 `community.codegoai.com` 的 DNS 和 TLS；正式切流前可先使用受限测试域名。

完成标准：NodeBB 可启动、重启后数据保留、HTTPS 正常、备份能够恢复到空环境。

### 阶段 1：先做身份闭环（本地已完成，待生产部署）

1. 在 `new-api` 增加 OAuth2/OIDC Provider。
2. NodeBB 安装或开发 CodeGo OIDC 插件。
3. 使用 `ExternalId` 作为 `sub`，完成首次登录、重复登录、改名和账号封禁测试。
4. 确认两个域名 Cookie 隔离。

完成标准：用户只在主站管理密码，社区没有第二套注册密码；被封禁账号不能获得新社区会话。

### 阶段 2：完成基础社区与治理（代码已实现，待容器验收与部署）

1. 开发 CodeGo AI 主题和跨板块广场首页。
2. 建立七个一级板块与贡献身份组，保留自由发帖。
3. 公开阅读，CodeGo 账号即可参与，沿用 NodeBB 举报和审核能力。
4. 实现首期服务端站外商业导流拦截。

完成标准：本地注册关闭；私信聊天关闭；高置信度站外商业导流在服务端被拒绝，普通技术链接仍可发布。

### 阶段 3：连接渠道业务（已完成首批只读接口）

1. 在 `new-api` 增加社区账号状态和公开渠道摘要接口；所有权写操作与真实消费者校验随对应功能实现。
2. 开发 NodeBB 只读渠道主主页插件（代码已实现，待容器与浏览器验收）。
3. 上线渠道公告、正式反馈和站内活动。
4. 建立 Webhook Outbox 和社区幂等消费。

当前完成标准：未知、停用或未认证渠道主不可显示；页面只展示公开、审核通过且活跃或降级的渠道；主站不可用时返回 503 并失败关闭。正式反馈与渠道内容写操作尚未进入该完成范围。

### 阶段 4：改造主站前端

1. 修改公开导航并加入社区入口。
2. 新增渠道详情和渠道主主页。
3. 市场条目加入公告、反馈和社区讨论入口。
4. 渠道主工作台加入社区待办摘要。

完成标准：用户能从市场进入渠道业务详情，再进入对应社区讨论；社区也能返回主站实时业务页。

### 阶段 5：灰度上线

1. 先邀请少量渠道主和真实消费者。
2. 观察审核量、广告绕过方式、接口延迟和 WebSocket 资源占用。
3. 修正规则后再开放普通用户申请准入。
4. 依据实际治理负担决定是否长期保持私信与实时聊天关闭。

## 13. 首期明确不做

- 不 fork 或魔改 NodeBB 核心。
- 不把 NodeBB 部署到主业务服务器。
- 不共享数据库、Redis 或 Cookie。
- 不把社区页面 iframe 到主站。
- 不将社区热度用于渠道质量排名。
- 不在首期同步所有社区通知到主站。
- 不在首期开放无限制私信和实时聊天。
- 不允许渠道主填写任意广告跳转地址。

## 14. 验收与验证

### 14.1 业务验收

- 主站账号可以登录社区，改名后不会创建重复账号。
- 主站封禁后不能重新登录；现有社区 Session 的即时撤销需在签名 Webhook 和后台会话撤销实现后验收。
- 未认证、停用或不存在的渠道主不显示渠道主页。
- 渠道主页只显示该渠道主的公开、审核通过且状态可用的渠道。
- 站外链接、短链、二维码和联系方式引流均被拦截或进入审核。
- 社区宕机不影响主站 API、市场、充值和结算。
- 主站短暂不可用时普通社区内容仍可阅读，渠道主页明确返回 503，不使用过期身份兜底。
- 桌面和移动端不存在文字遮挡、横向溢出或不可操作控件。

### 14.2 `new-api` 验证命令

```powershell
go test ./internal/identity/... ./internal/marketplace/... ./internal/community/...
Set-Location 'web/default'
bun run typecheck
bun run lint
bun run build
```

社区仓库还需要独立的插件单元测试、OIDC 集成测试、Playwright 关键流程测试，以及数据库备份恢复演练。具体命令在创建 `codego-community` 仓库并确定 NodeBB 版本后写入该仓库。
