# CodeGo 每日幸运号与月卡等级权益设计文档

> 状态：已确认方案，待实现
> 日期：2026-08-01
> 版本：v1.0
> 适用范围：Lite、Standard、Pro、Ultra 月卡，套餐购买、续费、升级、每日开奖、额度入账与盲盒赠送
> 设计原则：额度交易为主、活动权益为辅、规则简单透明、成本固定可控、奖励全程可审计

## 1. 文档目标

本文档定义 CodeGo 月卡等级视觉、唯一编号、每日幸运号活动和盲盒赠送权益，作为产品、设计、前端、后端、运营与测试的共同基线。

核心方案：

- 用户购买月卡后获得一个永久唯一的月卡编号，以及一个用于每日开奖的四位幸运尾号。
- 每天全站公布一个四位开奖号码，按尾号匹配位数向对应月卡追加普通额度。
- Lite、Standard、Pro、Ultra 使用不同等级色和小幅奖励系数。
- 购买或续费月卡继续赠送盲盒；盲盒负责即时反馈，每日幸运号负责持续期待。
- 所有中奖奖励进入统一额度钱包，不进入月卡专属额度，不形成用户之间的流动市场。

## 2. 产品定位

### 2.1 本质

CodeGo 的核心商业关系仍然是用户购买月卡额度。每日幸运号和盲盒都是随月卡附赠的活动权益，不是独立出售的金融资产或抽奖商品。

### 2.2 目标

- 让不同等级月卡在已购套餐和编号展示中具有稳定、清晰的身份差异。
- 给月卡用户提供每天一次、无需复杂学习的持续活动。
- 通过较大的名义额度奖励制造吸引力，同时利用低额度成本控制实际支出。
- 让购买、开奖、中奖、入账和累计奖池全部可追踪、可重试、可审计。
- 保留现有盲盒价值，但不再建设四套独立盲盒奖池。

### 2.3 非目标

- 不做 Token、积分币、交易市场或用户间转赠。
- 不做挖矿、质押、复利、收益率或额度投资。
- 不允许单独购买每日开奖次数。
- 不允许押注、销毁或损失用户已经购买的月卡额度。
- 不将活动绑定到平台无法控制的新模型上线。
- 不用幸运编号替代账号 UID。

## 3. 核心规则摘要

| 项目 | 规则 |
|---|---|
| 活动名称 | 每日幸运号 |
| 开奖频率 | 每天一次 |
| 默认开奖时间 | 20:00，Asia/Shanghai |
| 参与对象 | 开奖快照时处于有效状态且开启活动权益的月卡订阅 |

## 4. 月卡等级系统

### 4.1 等级配置

| 月卡 | 等级键 | 主色 | 浅色背景 | 每日奖励系数 | 每周期赠送盲盒 |
|---|---|---|---|---:|---:|
| Lite | `lite` | `#64748B` | `#F1F5F9` | 1.0 | 1个 |
| Standard | `standard` | `#2563EB` | `#EFF6FF` | 1.1 | 2个 |
| Pro | `pro` | `#7C3AED` | `#F5F3FF` | 1.2 | 3个 |
| Ultra | `ultra` | `#B7791F` | `#FFFBEB` | 1.3 | 5个 |

等级不能继续通过套餐标题字符串推断。`subscription_plans` 应增加明确的 `membership_tier` 字段，并由后台套餐表单配置。

### 4.2 颜色应用范围

等级色只用于：

- 已购买月卡的等级图标、套餐名称和完整编号。
- 幸运尾号、等级徽标和额度进度条。
- 每日幸运号页面中的月卡行和中奖记录。
- 用户下拉菜单中的最高优先级月卡摘要。

购买、续费、升级等主要按钮继续使用网站现有暖橙品牌色，不按月卡等级改变按钮颜色。等级必须同时使用文字和颜色表达，不能只依赖颜色。

## 5. 月卡编号设计

### 5.1 为什么不能只使用四位编号

四位数字只有10,000种组合，不能承担永久唯一身份。方案将“月卡唯一编号”和“每日开奖尾号”拆分：

~~~text
PRO · CG-7K2M9Q-7316
      └──────┘ └──┘
       唯一前缀  幸运尾号
~~~

- 完整编号 `CG-7K2M9Q-7316` 全局唯一，用于展示、查询和历史审计。
- 幸运尾号 `7316` 允许重复，只用于每日开奖。
- `PRO` 是当前套餐等级徽标，不写入永久编号；升级后编号不变。

### 5.2 生成规则

- 唯一前缀使用六位无歧义 Base32 字符，排除 `0/O`、`1/I` 等易混字符。
- 幸运尾号使用四位数字字符串，必须保留前导零，例如 `0047`。
- 使用 Go `crypto/rand` 生成，不得使用 `math/rand`。
- 数据库为完整编号建立唯一索引；冲突时最多重试5次，失败必须上报并回滚订阅权益发放。
- 幸运尾号不建立唯一约束，可以被不同月卡同时持有。

### 5.3 生命周期

| 场景 | 编号处理 |
|---|---|
| 首次购买 | 生成完整编号和幸运尾号 |
| 提前续费 | 保留完整编号和尾号，延长参与时间 |
| 套餐升级 | 保留编号，下一次开奖使用新等级系数 |
| 新购另一张月卡 | 为新订阅生成新编号 |
| 月卡失效或取消 | 保留历史编号，停止参与开奖 |
| 月卡删除 | 中奖历史和编号记录不得级联物理删除，应保留审计引用 |

## 6. 每日开奖规则

### 6.1 基础奖励

只领取最高匹配档，不重复叠加：

| 结果 | 精确概率 | 基础奖励 |
|---|---:|---:|
| 仅匹配1位 | 9% | 0.25 统一额度 |
| 仅匹配2位 | 0.9% | 2.5 统一额度 |
| 仅匹配3位 | 0.09% | 12.5 统一额度 |
| 4位全部匹配 | 0.01% | 25 统一额度 + 累计奖池 |
| 未中奖 | 90% | 0 统一额度 |

示例：

~~~text
月卡幸运尾号：7316
今日开奖号码：5816
匹配结果：尾号两位
Pro 奖励：2.5 统一额度 × 1.2 = 3 统一额度
~~~

基础奖励按统一额度保留两位小数后转换为系统 quota 单位；统一额度迁移后不再乘以旧 GPT 额度的 0.25 换算系数。

### 6.2 累计奖池

- 初始值：25 统一额度。
- 当天无人四位全中：增加 5 统一额度。
- 封顶值：250 统一额度。
- 当天有人四位全中：每个中奖号先获得 `25 统一额度 × 等级系数`，累计奖池由全部四位中奖号等额平分。
- 累计奖池不乘等级系数。
- 命中后的下一期开奖将奖池重置为 25 统一额度。

### 6.3 参与快照

每天开奖时，只有同时满足以下条件的订阅参与：

- `status = active`。
- `start_time <= draw_time < end_time`。
- 对应套餐 `plan_type = monthly`。
- 对应套餐已启用每日幸运号权益。
- 已成功分配月卡编号。

当日开奖时间之后购买的月卡从次日开始参与。多张有效月卡分别作为独立参与项，奖励分别进入对应订阅。

## 7. 成本模型

### 7.1 单张月卡基础期望

~~~text
9% × 0.25
+ 0.9% × 2.5
+ 0.09% × 12.5
+ 0.01% × 25
= 0.05875 统一额度 / 天
~~~

按30天和统一额度实际成本 `0.1元/1统一额度` 计算：

| 月卡 | 月均发放额度 | 月均实际成本 |
|---|---:|---:|
| Lite | 1.76 统一额度 | 约0.18元 |
| Standard | 1.94 统一额度 | 约0.19元 |
| Pro | 2.12 统一额度 | 约0.21元 |
| Ultra | 2.29 统一额度 | 约0.23元 |

累计奖池单独统计，不包含在以上期望中。运营后台必须展示参与月卡数、名义发放额度、按配置成本折算后的实际成本和当月预算使用率。

### 7.2 预算保护

- 累计奖池每日增量、封顶值和活动开关必须后台可配置。
- 配置修改仅影响下一次尚未创建的开奖，不能修改历史开奖。
- 超过月度预算预警线时只告警，不得静默减少已经公布的奖励。
- 暂停活动后，已完成开奖但未入账的奖励仍必须继续结算。

## 8. 盲盒月卡权益

### 8.1 是否保留

保留。盲盒和每日幸运号承担不同职责：

- 盲盒：购买或续费成功后的即时反馈。
- 每日幸运号：月卡有效期内的持续期待和回访。
- 额度结转：后续可作为确定性权益单独设计，不与随机活动混合。

本期不建设四套独立盲盒奖池，继续使用现有统一盲盒奖池，只按月卡等级改变赠送数量。

### 8.2 发放规则

| 场景 | 发放规则 |
|---|---|
| 首次付费购买 | 按当前等级全量赠送 |
| 正常续费 | 每个新计费周期重新赠送一次 |
| 同周期升级 | 只补发新旧等级数量差额 |
| 同周期降级再升级 | 按本周期已发最大数量计算，不重复发放 |
| 管理员绑定 | 默认不自动赠送，由管理员明确选择 |
| 兑换码激活 | 由兑换码配置决定是否附带盲盒 |

盲盒权益记录使用 `user_subscription_id + benefit_cycle` 作为幂等边界。赠送盲盒默认与对应月卡周期同时到期，前端必须显示到期时间。

## 9. 用户流程

### 9.1 首次购买

~~~text
支付成功
  ↓
创建或激活月卡订阅
  ↓
生成唯一月卡编号和四位幸运尾号
  ↓
按等级赠送盲盒
  ↓
购买成功弹窗揭晓编号和盲盒数量
  ↓
次日开始参与每日开奖
~~~

### 9.2 每日开奖

~~~text
20:00 创建全站开奖号码
  ↓
快照有效月卡
  ↓
计算尾号匹配和等级奖励
  ↓
生成中奖记录
  ↓
额度进入对应月卡账本
  ↓
前端展示今日结果与新额度
~~~

### 9.3 续费和升级

- 续费保留编号，进入新权益周期并重新赠送盲盒。
- 升级保留编号，下一期开奖切换等级色与系数；本周期只补盲盒差额。
- 升级发生在开奖任务快照之前时，当日使用新等级；快照之后则从次日生效。

## 10. 页面信息架构

### 10.1 导航

新增用户路由 `/daily-lucky-number`，导航名称“每日幸运号”，放在个人区域的“套餐购买”和“盲盒”之间。

### 10.2 独立活动页

桌面端首屏使用主次两列，不做营销式大卡片或高饱和背景：

~~~text
┌─────────────────────────────────┬──────────────────┐
│ 每日幸运号       距开奖 01:42:18 │ 累计奖池          │
│                                 │ $460             │
│ 今日号码         5 8 1 6        │ 封顶 $1,000       │
│ 昨日结果         2 7 4 1        │ 今日20:00开奖      │
└─────────────────────────────────┴──────────────────┘

我的月卡号码
┌────────────────────────────────────────────────────┐
│ PRO月卡  CG-7K2M9Q-7316  1.2倍  剩18天  今日+$12 │
└────────────────────────────────────────────────────┘

[我的记录] [全站大奖]
日期        开奖号      月卡尾号      结果      入账
08-01       5816        7316          2位       +$12
~~~

移动端按“今日开奖、累计奖池、我的月卡、历史记录”顺序改为单列。

### 10.3 套餐页

在现有已购套餐面板中加入：

- 等级色图标与等级名称。
- 完整月卡编号。
- 四位幸运尾号。
- 今日开奖结果或下次开奖倒计时。
- “查看每日幸运号”入口。

示例：

~~~text
PRO月卡 · CG-7K2M9Q-7316
幸运尾号 7316 · 今日命中2位 +$12
剩余 $83.40 / $120 · 18天后到期
~~~

### 10.4 其他展示位置

1. 购买成功弹窗：首次揭晓完整编号，并显示赠送盲盒数量。
2. 控制台订阅卡片：显示紧凑徽标 `PRO · 7316` 和今日中奖状态。
3. 用户下拉菜单：只显示最高优先级有效月卡摘要，不替换账号 UID。
4. 账单或订阅历史：显示完整编号，支持复制。
5. 盲盒页：只显示盲盒余额和来源，不重复解释每日幸运号规则。

## 11. 视觉与交互规范

- 页面背景、面板和按钮保持现有产品设计系统，不为活动建立独立赌场风主题。
- 幸运号码使用等宽数字和 tabular numerals，固定单元宽度，开奖时不得导致布局跳动。
- 等级色只占小面积；正文、表格和规则仍使用中性前景色。
- 开奖动画控制在约800毫秒，仅在用户正在活动页时播放；后台自动开奖不依赖动画。
- `prefers-reduced-motion` 下直接显示开奖结果。
- 正文达到 WCAG AA 对比度；颜色之外必须同时显示等级文字。
- 所有时间同时显示日期和明确时区，避免“今天/昨天”跨时区歧义。

### 11.1 页面状态

| 状态 | 表现 |
|---|---|
| 加载中 | 固定尺寸骨架屏，不使用全页转圈 |
| 无有效月卡 | 简短说明权益，并提供“选购月卡”入口 |
| 今日未开奖 | 显示倒计时和昨日结果 |
| 未中奖 | 显示号码对比，不使用错误色 |
| 已中奖 | 显示匹配位数、奖励和入账后的额度 |
| 入账处理中 | 显示“奖励已确认，额度入账中” |
| 多张月卡 | 每张月卡独立一行，按订阅扣费优先级排序 |
| 服务异常 | 保留已生成号码，显示延迟状态，不重新开奖 |

## 13. API 设计

用户接口建议：

| 方法 | 路径 | 用途 |
|---|---|---|
| GET | `/api/daily-lucky-number/self` | 今日开奖、奖池、用户有效编号和当日结果 |
| GET | `/api/daily-lucky-number/history` | 用户中奖历史，分页 |
| GET | `/api/daily-lucky-number/public-wins` | 全站大额中奖记录，脱敏 |

`/api/subscription/self` 同时在每条订阅中返回编号摘要，供套餐页和控制台复用，避免页面额外串行请求。

管理接口建议：

| 方法 | 路径 | 用途 |
|---|---|---|
| GET/PUT | `/api/daily-lucky-number/admin/config` | 查看或更新下一期开奖配置 |
| GET | `/api/daily-lucky-number/admin/draws` | 查看开奖记录和成本 |
| POST | `/api/daily-lucky-number/admin/draws/:id/retry` | 重试失败入账，不重新生成号码 |
| POST | `/api/daily-lucky-number/admin/backfill` | 幂等补发缺失编号 |

## 14. 开奖与入账实现

### 14.1 任务归属

每日开奖任务运行在现有 `ledger-worker`，只允许主节点启动。Web 进程只读取结果，不能触发正式开奖。

### 14.2 幂等流程

1. 以 `draw_date` 唯一键创建当日开奖，已经存在则恢复处理而非重新生成号码。
2. 固化开奖号码和开奖前奖池。
3. 快照有效月卡并创建奖励记录，联合唯一键防止重复。
4. 分批处理奖励，避免一个大事务锁住全部订阅。
5. 每笔奖励在事务内锁定订阅、增加 `amount_total`，必要时增加 `period_amount`。
6. 同时写入 Billing Ledger。
7. 全部奖励完成后结算奖池并将开奖标记为 completed。

账本建议使用：

~~~text
reason_code: subscription_lucky_draw
reference_type: subscription_lucky_reward
idempotency_key: lucky-draw:{draw_date}:{user_subscription_id}
~~~

不得只修改 `user_subscriptions.amount_total` 而不写账本。已生成开奖但入账失败时，必须重试原奖励，不能重新随机。

## 15. 存量月卡补发

上线时执行一次可重复运行的补发任务：

1. 查询所有当前有效的 monthly 订阅。
2. 根据套餐配置识别会员等级。
3. 对缺少 `subscription_lucky_numbers` 的订阅生成编号。
4. 使用 `INSERT ... ON CONFLICT DO NOTHING` 或等价事务保证并发安全。
5. 输出扫描数、已存在数、新增数、失败数和失败订阅ID。

补发完成后，存量用户从下一次开奖开始参与。补发编号不追溯历史开奖，也不补发过去日期奖励。

## 16. 管理后台

在订阅管理中增加“每日幸运号”页签，提供：

- 活动启停和开奖时间。
- 基础奖励 `0.25/2.5/12.5/25 统一额度`。
- 等级系数 `1.0/1.1/1.2/1.3`。
- 奖池初始值、每日增量和封顶值。
- 今日参与月卡数、中奖数、名义额度和实际成本。
- 月度预算、预算使用率和预警。
- 开奖历史、失败奖励和幂等重试。
- 存量编号补发结果。

已经创建的开奖记录及其配置快照只读。修改配置必须明确提示“从下一期开奖生效”。

## 17. 公平性、安全与合规边界

- 开奖号码使用密码学安全随机源。
- 可使用提交-揭示记录保存开奖随机种子摘要，便于事后验证未在开奖后改号；该机制不增加用户操作步骤。
- 全站中奖记录只显示套餐等级、脱敏编号和奖励，不泄露用户身份。
- 概率、奖励、奖池分配、有效期和入账规则必须公开。
- 开奖次数不能单独出售，奖励不能提现、交易或转赠。
- 不展示伪造中奖记录，不使用虚假倒计时或人为“差一点中奖”结果。
- 上线前依据实际经营地区检查有奖销售和随机奖励相关规定。

## 18. 分阶段交付

### 阶段一：后端闭环

- 数据迁移和套餐等级字段。
- 编号生成、存量补发和购买链路接入。
- 每日开奖、累计奖池和订阅账本入账。
- 用户查询与管理接口。

### 阶段二：核心页面

- 套餐页已购月卡编号与等级色。
- 每日幸运号独立页面。
- 购买成功编号揭晓。
- 控制台订阅摘要。

### 阶段三：盲盒与运营

- 月卡周期盲盒幂等发放。
- 管理后台配置、成本统计和失败重试。
- 全站中奖记录和活动规则页。

## 19. 测试与验收标准

### 19.1 后端

- 四位号码包含前导零时能够正确生成、存储和匹配。
- 0、1、2、3、4位匹配边界均有单元测试。
- 多个月卡拥有相同幸运尾号时均能中奖。
- 多个四位中奖者正确平分累计奖池。
- 同一天重复执行任务不会重复开奖或重复入账。
- 任务在创建奖励、订阅更新、账本入账各阶段中断后均可恢复。
- 续费保留编号，升级切换系数，新购月卡生成新编号。
- 存量补发重复运行不新增重复记录。
- 盲盒首次购买、续费、升级差额和重复回调均满足幂等要求。

### 19.2 前端

- 套餐页、活动页、控制台和购买结果展示同一编号与等级。
- 多张月卡、无月卡、开奖前、未中奖、已中奖、入账中和异常状态完整。
- 320px移动端无横向溢出，长编号可复制且不会挤压额度信息。
- 明暗主题下四档颜色、正文和弱化文本满足可读性要求。
- 键盘可以访问页签、复制编号和历史分页。
- 减弱动效模式不播放滚动开奖动画。

### 19.3 运营验收

- 后台统计的参与数、中奖数和发放总额可与数据库记录核对。
- 实际成本计算使用可配置的 `0.1元/1统一额度`，不把名义额度误当现金成本。
- 暂停活动不会丢失已经产生的中奖奖励。
- 任何历史开奖都能追溯到参与订阅、幸运尾号、等级系数和账本流水。

## 20. 已确认决策

| 决策 | 结论 |
|---|---|
| 活动形式 | 每日全站统一幸运号，不建设币圈式流动市场 |
| 开奖频率 | 每天一次 |
| 奖励梯度 | 0.25 / 2.5 / 12.5 / 25 统一额度 |
| 等级差异 | 1.0 / 1.1 / 1.2 / 1.3 小幅系数 |
| 头奖 | 四位基础奖励加公共累计奖池 |
| 编号容量 | 完整编号全局唯一，四位尾号允许重复 |
| 奖励去向 | 加入统一额度钱包 |
| 盲盒权益 | 保留统一奖池，按等级赠送1/2/3/5个 |
| 用户操作 | 自动参赛、自动开奖、自动入账 |
| 账号关系 | 月卡编号不替代用户UID |
