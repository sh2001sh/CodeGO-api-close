# 用户渠道市场与分组排行榜设计方案

> 文档状态：设计评审稿 v0.3
> 最后更新：2026-08-15
> 适用项目：new-api
> 关联方案：工作区根目录 `GPT通用额度反转改造方案.md`
> 目标：允许用户提交自有渠道、形成独立市场分组，并通过检测、状态管理、搜索和排行榜向其他用户提供服务。

## 1. 执行摘要

本功能把用户自有上游渠道建设成一个受平台治理的“渠道市场”：渠道主提交渠道和密钥、设置公开倍率，系统为其创建独立分组；通过检测和审核后，该分组可以被其他用户选择。消费者使用市场分组时只消耗通用额度，消费结算按平台规则拆分后进入渠道主的待结算余额。

核心闭环：

```text
渠道主提交渠道
  -> 加密保存凭据
  -> 创建独立市场分组
  -> 自动检测与风险审核
  -> 发布到分组市场/排行榜
  -> 消费者使用通用额度调用
  -> 记录请求质量与扣费
  -> 平台扣除 5% 佣金 + 1% 交易手续费
  -> 94% 进入渠道主待结算余额
  -> 风险观察期结束后转为可用、可消费、可转账余额
```

本方案不直接开放现有管理员 `/api/channel` 能力。用户渠道使用独立领域实体和用户权限接口，审核通过后再映射到内部 `Channel` 与路由分组，避免普通用户接触管理员渠道、其他用户密钥或系统级路由配置。

## 2. 目标与非目标

### 2.1 本期目标

- 用户可以创建、编辑、验证、暂停和删除自己的渠道。
- 每个用户渠道默认创建一个独立市场分组，分组名全局唯一且内部标识稳定。
- 分组具备明确的生命周期状态、检测状态和公开可用状态。
- 市场页支持搜索、筛选、排序、分页和排行榜。
- 排行榜展示成功率、平均首字时间（TTFT）、平均总延迟、TPS、请求量和倍率。
- GPT 类渠道支持协议兼容、流式响应、模型列表和性能检测。
- 用户上传分组的请求只消耗《GPT 与通用额度反转改造方案》定义的通用额度，并在日志中明确标识。
- 只有平台官方分组可以对 GPT/Codex/Responses 使用 GPT 套餐额度和 GPT 专属额度。
- 消费收入通过不可变账本进入渠道主待结算账户，不能提现，但可用于消费或按现有支付密码规则转账。
- 管理员可以审核、暂停、下架、重新检测和查看风险证据。

### 2.2 非目标

- 本期不开放现金提现。
- 本期不允许渠道主修改底层系统路由规则或查看平台其他渠道。
- 本期不承诺通过探针绝对证明模型身份；检测结果仅作为准入和风险证据。
- 本期不做渠道之间的自动搬运、密钥共享或公开密钥展示。
- 本期不允许 GPT 套餐额度或 GPT 专属额度支付市场渠道。
- 本期不直接合入未取得商业授权的第三方检测器源码。

## 3. 设计原则

1. **用户渠道与管理员渠道隔离**：市场实体负责所有权、审核和结算，内部渠道只承担实际转发。
2. **密钥永不回显**：密钥只允许创建或替换，不提供明文读取接口。
3. **先锁定分组来源，再决定额度池**：平台官方分组遵循原额度反转方案；用户上传分组无论声明什么模型都强制使用通用额度。
4. **排名不能被小样本操纵**：公开原始指标，正式排名使用置信修正、样本门槛和异常惩罚。
5. **收益必须可审计**：消费扣款、平台费用、待结算、释放、退款和转账全部产生幂等账本记录。
6. **状态不能只靠颜色表达**：所有状态同时使用文本、图标和可访问说明。
7. **检测与生产转发隔离**：检测任务使用受限网络、短期凭据引用和独立并发配额。

## 4. 角色与权限

| 角色 | 主要能力 | 明确限制 |
|---|---|---|
| 消费者 | 搜索分组、查看排名与检测摘要、选择分组、查看自己的使用日志 | 不能查看渠道密钥、内部地址、渠道主真实身份或完整检测探针 |
| 渠道主 | 创建渠道、设置倍率、查看检测、暂停分组、查看收入和请求质量 | 不能购买自己的分组产生收益，不能修改排名数据，不能提现 |
| 管理员 | 审核、重新检测、限流、暂停、下架、查看完整证据和账本 | 人工补偿必须写入账本和审计日志，不能直接改余额快照 |
| 检测任务 | 读取一次性凭据引用、执行协议与性能检测、写入报告 | 不能读取用户余额，不能执行转账，不能把密钥写入日志 |

## 5. 核心领域模型

### 5.1 MarketplaceChannel

代表渠道主提交的上游连接配置，不直接向消费者公开。

建议字段：

| 字段 | 说明 |
|---|---|
| `id` | 市场渠道 ID |
| `owner_user_id` | 渠道主用户 ID |
| `provider_type` | OpenAI Compatible、Codex、Azure OpenAI 等 |
| `base_url_ciphertext` | 加密后的上游地址；公开页只显示脱敏域名或“不公开” |
| `credential_ref` | 密钥保管系统中的凭据引用，不存明文 |
| `credential_version` | 密钥轮换版本 |
| `declared_models` | 渠道主声明支持的模型 |
| `status` | 渠道内部状态 |
| `internal_channel_id` | 审核通过后映射的内部渠道 ID |
| `created_at` / `updated_at` | 创建和更新时间 |

### 5.2 MarketplaceGroup

代表消费者可见、可选择、可排名的独立分组。首期采用“一渠道一分组”，数据模型保留未来一组多渠道的能力。

| 字段 | 说明 |
|---|---|
| `id` | 市场分组 ID |
| `public_slug` | 稳定公开标识，由系统根据分组 ID 生成 |
| `system_display_name` | 消费者看到的系统分组名，由倍率与短 ID 生成，如 `用户分组 0.82x · #A7K2` |
| `internal_group_name` | 内部路由分组名，由倍率基点与不可猜 ID 生成，如 `market_u0082_01J...` |
| `owner_user_id` | 渠道主 |
| `source_type` | 固定为 `marketplace_user`；平台官方分组使用独立系统记录的 `official`，用户不可修改 |
| `owner_display_name` | 渠道主公开昵称，仅作为来源说明，不作为分组名 |
| `multiplier` | 渠道主设置的消费倍率 |
| `credit_pool_policy` | 固定为 `marketplace_universal_only` |
| `routing_version` | 倍率变更时递增，用于新旧内部路由组平滑切换 |
| `lifecycle_status` | 生命周期状态 |
| `visibility` | `private`、`unlisted`、`public` |
| `published_at` | 首次公开时间 |

### 5.3 其他实体

- `ChannelCredential`：加密凭据、密钥版本、轮换时间和撤销状态。
- `ChannelVerificationRun`：一次检测任务及其版本、阶段、结果、证据摘要和过期时间。
- `GroupMetricSnapshot`：按分组、模型和时间窗聚合的质量指标。
- `GroupRankingSnapshot`：榜单计算版本、名次、综合分和惩罚项。
- `MarketplaceSettlement`：一次消费者请求对应的总扣费、平台费用和渠道主收入。
- `MarketplaceTransferTrace`：渠道收入转入用户可转账余额后的来源追踪。
- `MarketplaceRiskEvent`：自消费、关联账号、异常成功率、突增流量和争议记录。

## 6. 分组状态机

```text
draft
  -> verifying
  -> pending_review
  -> active
  -> degraded
  -> suspended
  -> disabled
```

| 状态 | 用户可见含义 | 是否接收新流量 | 进入条件 |
|---|---|---:|---|
| `draft` | 草稿 | 否 | 已创建但资料或密钥未完成 |
| `verifying` | 检测中 | 否 | 正在执行基础或专项检测 |
| `pending_review` | 待审核 | 否 | 自动检测通过，等待风控或人工审核 |
| `active` | 可用 | 是 | 检测、审核、结算配置均有效 |
| `degraded` | 质量下降 | 受限 | 短期成功率或延迟越过降级阈值 |
| `suspended` | 已暂停 | 否 | 渠道主暂停、风控暂停或连续故障 |
| `disabled` | 已下架 | 否 | 渠道主删除、管理员下架或长期失效 |

检测状态与生命周期状态分开保存，避免“检测过期”覆盖“管理员暂停”：

```text
verification_status: never_run | queued | running | passed | failed | expired
```

建议自动治理规则：

- 最近 5 分钟请求数至少 20 且成功率低于 80%：进入 `degraded`，降低路由权重。
- 最近 15 分钟请求数至少 50 且成功率低于 60%：自动 `suspended`。
- 连续健康 30 分钟且重新检测通过：从 `degraded` 恢复 `active`。
- 密钥替换、Base URL 变更或模型集合重大变更：强制重新检测，公开分组暂时不接新流量。
- 完整检测报告建议 7 天过期；轻量健康检测持续运行。

阈值必须由管理员配置，并按模型类型区分，避免长推理模型被普通聊天模型的延迟阈值误判。

## 7. 创建、检测与发布流程

### 7.1 渠道主提交

创建表单只收集必要信息：

- 不允许用户填写分组名；渠道信息按管理员添加渠道的连接配置方式填写。
- 渠道协议类型与 Base URL。
- API Key 或对应凭据。
- 声明支持的模型。
- 消费倍率。
- 是否公开参与排行榜。

提交后立即完成：

1. 校验 URL 仅允许 `https`，阻止内网、环回、云元数据地址和 DNS 重绑定。
2. 加密保存凭据，响应中只返回密钥尾号和版本。
3. 创建 `MarketplaceChannel` 与 `MarketplaceGroup` 草稿。
4. 系统按倍率与分组 ID 生成展示名和内部 group 名，禁止用户自定义或通过 API 覆盖。
5. 投递检测任务，不在 HTTP 请求内同步执行大量探针。

系统命名规则建议：

```text
system_display_name = 用户分组 {multiplier}x · #{short_id}
internal_group_name = market_u{multiplier_bps}_{opaque_group_id}

示例：
用户分组 0.82x · #A7K2
market_u0082_01JDX7M4Y...
```

- `short_id` 只用于识别，不包含用户 ID、渠道主昵称、域名或模型宣传词。
- Token 绑定保存稳定的 `marketplace_group_id`，不直接保存可变展示名。
- 倍率变更生效时创建新的 `routing_version` 和内部 group 名；旧版本只承接已开始请求并在排空后停用，避免直接重命名破坏线上 Token。
- 渠道主昵称仅作为来源信息展示，不能通过其他字段恢复广告式分组名。

### 7.2 检测阶段

检测分为四层，失败时明确显示失败层级和可操作原因：

1. **基础安全检测**：URL、TLS、DNS、重定向、证书和出站网络策略。
2. **协议检测**：模型列表、Chat Completions、Responses/Codex、流式格式、错误响应和取消请求。
3. **能力检测**：声明模型是否可用、上下文限制、工具调用、流式首字和输出完整性。
4. **性能检测**：成功率、TTFT、总延迟、TPS、并发稳定性和短时错误率。

检测报告公开页只展示结论摘要、检测时间、协议覆盖和脱敏指标。完整错误体、请求样本和网络证据仅管理员与渠道主可见，并继续执行脱敏。

### 7.3 审核与发布

- 自动检测通过后进入 `pending_review`。
- 首次发布、敏感域名、异常倍率或高风险账号必须人工审核。
- 审核通过后创建或更新内部 `Channel`，绑定唯一内部 group，并设置所有者和市场来源元数据。
- 内部渠道启用成功后，市场分组才切换为 `active`。
- 发布操作使用幂等键，避免重复创建内部渠道或重复上榜。

## 8. GPT 检测器集成与许可边界

用户指定的 `chen-006/gpt56_api_detector` 当前使用 **PolyForm Noncommercial License 1.0.0**。该许可证禁止将软件用于商业检测、会员功能、返佣、商业引流或预期商业应用。当前渠道市场具有收费、佣金和商业导流属性，因此在未获得作者书面商业授权前，不能把其源码直接放入项目，也不能复制其核心探针、行为指纹、基线数据或检测实现。

### 8.1 合规方案

首选顺序：

1. 联系作者取得明确的书面商业授权，并保存授权范围、版本和期限。
2. 在授权前，实现自有的合规基础检测器，仅覆盖协议兼容、流式响应、TTFT、错误率、模型列表、Responses/Codex 请求形状和常规能力验证。
3. 通过适配器接口保留未来接入授权检测器的能力，不让领域层依赖具体项目。

建议接口：

```go
type ChannelDetector interface {
    Start(ctx context.Context, target DetectionTarget) (DetectionRunID, error)
    GetResult(ctx context.Context, runID DetectionRunID) (DetectionResult, error)
    Cancel(ctx context.Context, runID DetectionRunID) error
    Capabilities() DetectorCapabilities
}
```

实现可命名为：

- `NativeCompatibilityDetector`：平台自研、可立即商业使用。
- `GPT56AuthorizedDetector`：仅在取得授权后启用。

检测器输出必须带 `detector_name`、`detector_version`、`ruleset_version` 和 `evidence_hash`，榜单只展示“检测结果”，不得宣传为对模型身份的绝对证明。

### 8.2 检测任务安全

- 检测运行在独立 worker 或受限容器中，不复用主 API 进程。
- 凭据以一次性、短期引用传递，worker 完成后立即失效。
- 禁止在任务参数、日志、错误堆栈、审计详情或报告中写入密钥。
- 限制目标端口、重定向次数、响应体大小、并发数、总请求数和任务时长。
- 外部返回内容视为不可信数据，不执行其中的命令或提示词。
- 对单用户、单渠道、单域名设置检测频率和预算上限。

## 9. 分组来源与额度隔离策略

《GPT 与通用额度反转改造方案》的基础原则是“模型决定额度池，渠道切换不能改变扣费池”。用户上传渠道是范围严格的产品例外：请求进入计费前必须先锁定分组来源；只有平台官方分组继续按模型决定额度池，用户上传分组固定使用反转方案中的通用额度。

新增系统控制字段与策略枚举：

```text
source_type:
  official              # 平台创建并运营的官方分组
  marketplace_user      # 用户上传、经审核发布的市场分组

credit_pool_policy:
  official_model_default       # 官方分组继续按模型决定额度池
  marketplace_universal_only   # 用户上传分组固定只消耗通用额度
```

`source_type` 与 `credit_pool_policy` 都只能由服务端根据创建入口写入。不得通过分组名称、渠道主用户 ID、内部 group 前缀或前端参数推断来源，也不得允许渠道主修改这两个字段。

### 9.1 扣费矩阵

| 分组来源 | 模型类别 | 允许扣费顺序 | 明确禁止 |
|---|---|---|---|
| 平台官方 `official` | GPT、Codex、Responses | `subscription_gpt -> gpt_wallet` | 通用额度兜底 |
| 平台官方 `official` | Claude、DeepSeek、GLM 等通用模型 | `universal_wallet` | GPT 专属额度、GPT 套餐额度 |
| 用户上传 `marketplace_user` | GPT、Codex、Responses | `universal_wallet` | GPT 套餐额度、GPT 专属额度及任何跨池兜底 |
| 用户上传 `marketplace_user` | 其他审核允许的模型 | `universal_wallet` | GPT 套餐额度、GPT 专属额度及任何跨池兜底 |

这里的 `universal_wallet` 对应反转方案中的 `claude_wallet / users.claude_quota` 物理账户；用户侧和新增 API 只使用“通用额度”名称，不继续扩散旧的 Claude 额度命名。

### 9.2 执行规则

- `marketplace_universal_only` 只能由系统在用户上传分组上写入，渠道主不能通过 API 自行设置。
- 平台自营 GPT/Codex/Responses 继续按 `subscription -> gpt_wallet` 扣费。
- 用户上传分组只读取通用额度，不查询 GPT 套餐或 GPT 专属钱包是否有余额，避免错误优先级和侧信道泄露。
- 路由解析完成后生成不可变 `billing_policy_snapshot`，至少记录 `source_type`、`credit_pool_policy`、模型类别、分组 ID 和策略版本。
- 预扣、最终结算、失败释放、退款和重试必须复用同一个策略快照；中途切换渠道不得重新选择额度池。
- 使用日志显示“用户渠道 · 仅通用额度”或“平台官方 · GPT 套餐/GPT 专属额度”，并记录实际扣费来源、费用拆分和策略版本。
- 用户上传分组的通用额度不足时直接失败，不跨池兜底，也不静默切换到官方分组。
- 管理员把用户渠道映射为内部 `Channel` 后，其来源仍然是 `marketplace_user`；审核通过不等于升级为官方渠道。

这样既满足市场渠道只能用通用额度的产品要求，也不会破坏平台自营模型的反转改造规则。

## 10. 倍率、计费与结算

### 10.1 倍率

- 渠道主设置倍率，后台配置允许的最小值、最大值和步长。
- 建议首期范围为 `0.50x - 3.00x`，步长 `0.01x`；超出常见区间触发人工审核。
- 调整倍率只影响新请求，已预扣或执行中的请求使用请求创建时的倍率快照。
- 排行榜同时展示倍率和质量指标，不能用综合分隐藏真实价格。

### 10.2 单次请求费用

```text
基础模型费用 = 输入费用 + 输出费用 + 其他按次费用
消费者应付 = 基础模型费用 x 渠道主倍率 x 活动倍率
平台佣金 = 消费者应付 x 5%
交易手续费 = 消费者应付 x 1%
渠道主收入 = 消费者应付 - 平台佣金 - 交易手续费
```

所有金额先使用整数额度计算，统一舍入规则，并在使用日志中展示完整公式和实际整数分录。失败请求按现有计费语义结算；若上游没有产生可计费结果，应释放预扣且不产生渠道主收入。

### 10.3 账本账户

建议新增账户类型或用途标签：

- `marketplace_consumer_reservation`：消费者通用额度预扣。
- `marketplace_platform_revenue`：平台佣金与手续费收入。
- `marketplace_owner_pending`：渠道主待结算余额。
- `marketplace_owner_available`：已释放、可消费和可转账余额。
- `marketplace_refund`：争议退款和补偿的对向分录。

默认结算规则：

1. 请求完成后原子结算消费者实际费用。
2. 6% 平台费用直接进入平台收入账户。
3. 94% 进入渠道主待结算账户。
4. 建议 24 小时风险观察期后释放到可用余额。
5. 可用余额进入现有通用额度钱包后，可以使用现有支付密码转账系统转给其他用户。

禁止直接修改 `users.quota` 或余额快照。结算、释放、退款和转账都必须通过账本服务，以请求 ID 和结算 ID 保证幂等。

### 10.4 防止循环套利

- 渠道主不能消费自己拥有的市场分组并产生收入。
- 同设备、同支付关系、同密钥来源、同域名控制权或高关联账户互刷进入风险队列。
- 待结算期内发现异常可冻结释放，但不能删除原始分录。
- 倍率明显低于上游成本不是平台补贴承诺，渠道主自行承担其上游成本。
- 平台应设置单分组流量突增保护和渠道主未结算风险敞口上限。

## 11. 指标体系

现有审计投影已经采集 `TtftMs`、`LatencyMs`、`Success`、`OutputTokens`、`GenerationMs`、`Group` 和 `Model`。方案应扩展现有投影与分组概览，不另建一套重复监控系统。

### 11.1 公开指标

| 指标 | 定义 | 展示建议 |
|---|---|---|
| 成功率 | 成功请求数 / 有效请求数 | 原始值 + 置信修正后的排名值 |
| 平均 TTFT | 有首字事件请求的 TTFT 平均值 | 毫秒；同时展示 P50/P95 |
| 平均总延迟 | 请求完成时间 - 请求开始时间 | 毫秒或秒；同时展示 P50/P95 |
| 平均 TPS | 输出 token / 生成阶段秒数 | tokens/s |
| 请求量 | 时间窗内有效请求数 | 24h、7d、30d |
| 独立消费者 | 去重消费者数量 | 仅显示数量，不公开身份 |
| 倍率 | 请求创建时使用的公开倍率 | `0.85x` 等 |
| 检测状态 | 最近检测结论和时间 | 通过、失败、过期、检测中 |
| 可用模型 | 检测通过且当前可路由的模型 | 支持搜索和筛选 |

### 11.2 成功率口径

以下请求不计入渠道质量分母：

- 用户主动取消且上游尚未开始处理。
- 平台自身鉴权、余额不足或全局限流导致的拒绝。
- 已确认的平台网络或审计系统故障。

以下请求计入失败：

- 上游 4xx/5xx、协议解析失败、流中断、超时和空响应。
- 渠道声明支持但实际不可用的模型。
- 由渠道容量不足导致的限流。

统计口径必须版本化，避免规则变更后历史榜单无法解释。

## 12. 排行榜设计

### 12.1 入榜门槛

- 24 小时榜：至少 100 个有效请求、10 个独立消费者、检测未过期。
- 7 天榜：至少 300 个有效请求、20 个独立消费者。
- 30 天榜：至少 1000 个有效请求、30 个独立消费者。
- 未达到门槛的分组显示“观测中”，可以搜索和查看，但不参与正式名次。

管理员可调整门槛，但修改后生成新的 `ranking_version`，不回写历史快照。

### 12.2 可靠性修正

不能直接按原始成功率排序。建议使用 Wilson 置信区间下界，默认 95% 置信水平：

```text
score_success = WilsonLowerBound(success_count, request_count, z=1.96)
```

这样 10/10 的小样本不会超过 9900/10000 的稳定分组。页面仍展示原始成功率，综合排名使用修正值并在说明中公开口径。

### 12.3 综合分

按同一模型、同一时间窗、同一协议类型建立比较 cohort，再将指标归一化到 0-100：

```text
综合分 =
  可靠性分 x 40%
  + TTFT 分 x 25%
  + 总延迟分 x 15%
  + TPS 分 x 10%
  + 价格竞争力分 x 10%
  - 风险与过期惩罚
```

- 可靠性分使用 Wilson 下界。
- TTFT、总延迟使用 P50 与 P95 的组合，低延迟得分更高。
- TPS 只对存在有效流式输出的模型参与；无此指标时按比例重分配权重，不能默认为 0。
- 价格分以同模型 cohort 的倍率分位数计算，避免不同成本模型直接比较。
- 检测过期、近期降级、争议率和异常流量产生明确惩罚项。
- 综合分最多保留一位小数，原始指标不因归一化而隐藏。

默认榜单按综合分排序，同时提供：成功率最高、首字最快、总延迟最低、倍率最低、请求最多和最近更新。

### 12.4 防刷榜

- 排名指标只使用真实结算请求，不使用渠道主触发的检测流量。
- 同一消费者的极高频请求在独立消费者指标中只计一次，并对异常模式降权。
- 渠道主及高关联账户请求不计收入，也不进入排名样本。
- 新分组设置 24 小时冷启动标识，不显示虚假“第 1 名”。
- 榜单按固定周期生成快照，不让单次请求实时改变名次。
- 对成功率突然跃升、延迟分布异常一致、流量来源单一进行风控标记。

## 13. 搜索、筛选与分页

搜索范围：

- 系统分组名和短 ID。
- 渠道主公开昵称。
- 可用模型名和协议类型。
- 分组公开短标识。

筛选项：

- 模型。
- 状态：可用、降级、观测中、暂停。
- 检测状态：已通过、即将过期、已过期。
- 时间窗：24 小时、7 天、30 天。
- 倍率区间。
- 最低成功率和最大 TTFT。

排序由后端执行，查询参数必须白名单化。默认每页 20 条，支持 20/50 条；不使用无限堆叠。数据库建议对 `system_display_name`、`public_slug`、`owner_display_name`、状态、发布时间和归一化模型名建立索引；PostgreSQL 可使用 trigram 或全文检索，其他数据库先采用标准化前缀搜索。

## 14. 页面信息架构

不新增侧边栏入口，扩展现有 `/group-status` 为“分组市场”，保留原有状态监控能力。

### 14.0 前端设计简报

**界面目的**：帮助消费者在较短时间内判断“哪个分组适合当前模型和预算”，帮助渠道主完成“提交、检测、发布、运营、结算”的完整闭环，同时让管理员能快速处理异常渠道。

**目标用户与场景**：

- 消费者主要在桌面端选择长期使用的 API 分组，也会在移动端快速查看分组是否故障。
- 渠道主主要在桌面端录入凭据、处理检测失败、调整倍率和查看收益。
- 管理员需要高密度列表和证据侧栏，不需要营销式卡片或大型数据装饰。

**设计情绪**：安静、可信、精确。延续现有 CodeGo 的暖铜强调色和产品控制台结构，但数据区以中性表面、清晰边界和语义状态色为主，不把排行榜做成游戏化榜单。

**视觉记忆点**：每个分组始终同时显示“来源、额度池、质量、价格、状态、检测新鲜度”六类证据；任何“选择分组”操作都能在提交前看见实际额度规则和费用示例。

**主要视口**：

- 桌面：1280-1920px，排行榜和渠道主运营的主要工作区。
- 平板：768-1279px，保留筛选和核心列，次要指标进入展开区。
- 移动：320-767px，使用紧凑行和详情页，不把桌面表格简单缩放。

### 14.0.1 页面导航模型

`/group-status` 顶部使用线型 Tabs，不新增侧边栏项目：

```text
[分组市场] [排行榜] [我的渠道]
```

- `分组市场`：默认页，面向消费者，按模型和价格筛选可用分组。
- `排行榜`：解释排名口径并进行多维质量比较。
- `我的渠道`：仅登录用户可见；没有渠道时展示创建入口和准入要求。
- 管理员在页面操作区看到“渠道治理”按钮，进入 `/group-status/admin`，普通用户不可见。
- 分组详情使用 `/group-status/groups/:slug`。
- 创建渠道使用 `/group-status/channels/new` 独立全页流程。
- 编辑渠道使用 `/group-status/channels/:id/edit`，密钥替换与普通资料编辑分开提交。

当前 `/group-status` 受登录保护，MVP 继续保持登录后可见。公开榜单属于后续能力，避免在权限、倍率和模型可见范围尚未稳定时公开不完整数据。

### 14.1 页面顶部

### 14.2 分组列表主表

桌面端使用高信息密度表格：

| 排名 | 分组 | 来源/额度 | 状态 | 倍率 | 成功率 | TTFT P50/P95 | 平均延迟 | TPS | 请求量 | 检测 | 更新时间 |
|---:|---|---|---|---:|---:|---:|---:|---:|---:|---|---|

交互要求：

- 表头支持排序，当前排序列和方向清晰可见。
- 行点击展开模型级指标、24 小时趋势、检测摘要和计费规则。
- 固定列宽和数字等宽字体，加载、状态变化不能造成表格跳动。
- 状态使用图标、文字和语义色，不只使用彩色圆点。
- 观测中分组显示样本进度，如 `62/100 请求 · 8/10 用户`。
- 分页固定在表格底部，滚动后仍能快速回到筛选区。

移动端不堆叠大型卡片，使用紧凑列表：首行显示分组、状态和倍率，第二行显示成功率、TTFT、延迟和请求量，点击进入详情抽屉或详情页。

### 14.3 分组详情

详情承担一个核心问题：“这个分组是否值得使用？”

- 顶部：分组名、状态、倍率、最近检测、选择此分组按钮。
- 质量概览：成功率、TTFT P50/P95、总延迟 P50/P95、TPS。
- 趋势：24h/7d 的成功率与延迟曲线。
- 模型列表：每个模型的独立指标和检测状态。
- 检测摘要：协议覆盖、检测器版本、时间和过期时间。
- 费用说明：根据来源展示固定额度规则；用户渠道只消耗通用额度，CodeGo 官方 GPT 分组展示 `GPT 套餐 -> GPT 专属额度`，并给出倍率示例。
- 风险提示：降级、样本不足、检测过期或近期变更。

### 14.4 渠道主工作台

工作台不与公开排行榜混用权限：

- 我的渠道：状态、密钥尾号、检测、倍率和操作。
- 质量：真实请求指标、错误类型、模型表现。
- 收入：今日收入、待结算、可用余额、平台费用和释放时间。
- 变更：替换密钥、修改倍率、暂停、重新检测。
- 审计：重要状态变更、管理员操作和结算异常。

### 14.5 关键界面状态

- 加载：使用稳定尺寸的行骨架，不使用全页 spinner。
- 空状态：区分“没有任何公开分组”和“筛选无结果”。
- 错误：保留筛选条件，提供重试并展示请求追踪 ID。
- 检测中：展示阶段和最后更新时间，不伪造百分比进度。
- 降级/暂停：禁用选择按钮，并说明恢复条件。
- 减弱动效：遵循 `prefers-reduced-motion`，状态切换只保留必要反馈。

### 14.7 排行榜界面

排行榜不是单一总榜，而是一个可解释比较工具：

```text
排行榜
[模型：gpt-5.6-sol] [24小时 | 7天 | 30天] [综合 | 稳定 | 首字 | 价格]

排名  分组       综合分  成功率(修正)  TTFT P50/P95  倍率  样本  趋势
1     用户分组 #A7K2 92.4 98.8%          580/1400ms    .82x  12k   ↑2
2     用户分组 #Q9M4 91.1 99.0%          640/1320ms    .91x  36k   -
```

- 榜单顶部固定显示当前模型、时间窗、样本门槛和生成时间。
- 原始成功率与 Wilson 修正值不可混写；表头使用 Tooltip 解释差异。
- 综合分展开后展示各分项和惩罚项，不提供不可解释的黑盒分数。
- “观测中”分组放在正式榜单之后的独立区域，不占名次。
- 趋势只表达相对上一个快照的名次变化，不使用闪烁或持续动画。
- 用户可固定最多 3 个分组进入比较栏，打开并排比较页；移动端最多比较 2 个。

### 14.8 分组详情与选择流程

详情页必须在首屏完成以下判断：

1. 当前模型是否可用。
2. 当前分组是否健康且检测未过期。
3. 倍率和预估费用是多少。
4. 选择后影响哪个 API Token。

```text
用户分组 0.82x · #A7K2          可用 · 2 小时前检测
gpt-5.6-sol  0.82x     成功率 99.2%  TTFT P50 580ms  P95 1.4s

费用预估
同模型基础消耗 $1.00 -> 本分组预计扣除通用额度 $0.82

分组来源
用户渠道 · 仅支持通用额度，不使用 GPT 套餐或 GPT 专属额度

应用到
(●) 指定 API Token  [选择 Token]
( ) 新建一个绑定此分组的 Token

[确认使用此分组]
```

关键决策：市场分组应绑定到 **API Token**，不应直接修改用户全局 `User.Group`。现有 Token 已有 `Group` 字段，这样可以让不同项目使用不同市场分组，也避免用户切换分组后所有线上项目同时受影响。

- Playground 可以提供仅当前会话有效的临时选择，不修改 Token。
- 确认页必须显示“分组来源”“实际额度池”“当前 Token”“模型范围”“失败回退规则”。
- 用户渠道使用固定警示文案：“仅扣通用额度；GPT 套餐和 GPT 专属额度在此分组不可用。”
- CodeGo 官方 GPT 分组使用固定说明：“优先扣 GPT 套餐额度，不足时扣 GPT 专属额度；不扣通用额度。”
- 如果 Token 已绑定其他分组，明确显示替换前后值，并要求二次确认。
- 分组暂停后，Token 保留绑定关系但请求返回可解释错误；不得静默回退到平台 GPT 分组并改扣 GPT 额度。
- 可选的“市场自动分组”必须是未来独立产品能力，只能在同为 `marketplace_universal_only` 的候选分组之间切换。

#### 14.8.1 选择器的来源分区

任何会改变 Token 分组的选择器都必须先按来源分区，不能把官方与用户渠道混成一个无标识下拉列表：

```text
选择分组

CodeGo 官方
  CodeGo GPT 标准组       GPT 套餐优先 · GPT 专属额度兜底

用户渠道
  用户分组 0.82x · #A7K2  仅通用额度 · 99.2% · TTFT 580ms
  用户分组 0.91x · #Q9M4  仅通用额度 · 98.9% · TTFT 640ms
```

- 默认不替用户预选来源；保留 Token 当前绑定并清晰标记。
- 搜索结果仍保留分区标题与来源标签，不因搜索而合并为单列表。
- CodeGo 官方行使用品牌图标与“官方”文本，用户渠道行使用中性渠道图标与短 ID；不使用易混淆的相近色作为唯一区别。
- 用户渠道选择结果必须再次展示“仅通用额度”；CodeGo 官方 GPT 分组再次展示“GPT 套餐优先，GPT 专属额度兜底”。
- 分组详情 URL、Token 绑定值和 API 请求都使用稳定 ID，不使用可变的倍率名称。

### 14.9 创建渠道全页流程

创建流程使用 4 个连续步骤，不使用弹窗：

```text
1 基本信息 -> 2 连接与模型 -> 3 倍率与容量 -> 4 检测与提交
```

**步骤 1：基本信息**

- 系统生成的分组名称预览和渠道主公开昵称；分组名称不可编辑。
- 是否公开参与排行榜。
- 渠道服务规则和上游授权声明勾选。

**步骤 2：连接与模型**

- 协议类型、Base URL、API Key。
- Base URL 失焦后仅做格式与安全预检，不发送模型请求。
- API Key 输入支持显示/隐藏，提交成功后只显示尾号。
- 获取模型列表后让渠道主勾选公开模型，不能默认全部发布。

**步骤 3：倍率与容量**

- 倍率数字输入 + Stepper，显示消费者费用示例和渠道主净收入示例。
- 声明最大并发、建议 QPS、每日服务时间或维护窗口。
- 显示 5% 佣金、1% 手续费、24 小时待结算规则。
- 倍率变更限制和生效时间必须在提交前可见。

**步骤 4：检测与提交**

- 展示将执行的检测阶段、预估请求数量、可能产生的上游成本。
- 检测过程按阶段显示：网络安全、协议、模型能力、性能。
- 阶段状态为等待、进行中、通过、失败，不伪造连续百分比。
- 失败项提供可复制的错误编号和针对性修复建议。
- 检测通过后提交审核；离开页面后任务继续运行，可在“我的渠道”查看。

草稿每一步自动保存非敏感字段；API Key 只在用户主动提交凭据时保存，不进入普通草稿 JSON。

### 14.10 我的渠道工作台

使用表格与行展开，不使用多层卡片：

| 分组 | 状态 | 倍率 | 24h 请求 | 成功率 | 待结算 | 可用收入 | 最近检测 | 操作 |
|---|---|---:|---:|---:|---:|---:|---|---|

行展开内容：

- 模型级质量、错误类型和容量利用率。
- 最近 10 次检测与配置变更。
- 待结算批次及预计释放时间。
- 暂停、恢复、重新检测、替换密钥和编辑资料操作。

危险操作约束：

- 暂停使用标准确认对话框；说明已有请求不受影响，新请求停止进入。
- 删除分组仅在没有未结算请求、没有开放争议、没有运行中检测时可执行。
- 替换密钥先验证新密钥，通过后原子切换；验证失败继续使用旧密钥。
- 倍率修改显示旧值、新值、生效时间和下次允许修改时间。

### 14.11 管理员治理界面

管理员页默认展示待处理队列，不以总量统计卡占据首屏：

- 待审核渠道。
- 检测失败或过期渠道。
- 自动暂停与风险事件。
- 待释放异常和退款异常。

选中一行后使用右侧详情面板展示资料、检测证据、风险关系、配置差异和操作历史。只有需要输入驳回原因、冻结期限或结算调整时才打开对话框。

管理员动作必须显示影响范围，例如“暂停后 3 个 Token 将无法继续调用此分组”，并要求填写审计原因。

### 14.12 前端视觉系统与组件约束

沿用现有控制台设计系统，不新建另一套品牌主题：

| 角色 | 使用方式 |
|---|---|
| 页面背景 | 现有 `background`，保持工作区安静 |
| 主表面 | `card` / `app-page-shell`，轻边界，不叠加大阴影 |
| 次级表面 | `muted`，用于筛选条、展开区和说明区 |
| 主要强调 | 现有铜色 `primary`，只用于主要动作、选中和焦点 |
| 成功 | `success`，表示健康或检测通过 |
| 警告 | `warning`，表示观测中、即将过期或降级 |
| 危险 | `destructive`，表示暂停、检测失败和不可逆动作 |

排版：

- 继续使用现有 Public Sans 与自然宽度中文字体回退。
- 页面标题使用现有 `SectionPageLayout` 规格，不使用营销页大标题。
- 表格正文 14px，辅助说明 12px，关键数字 14-16px 中等字重。
- 字距保持 0；数字使用 `tabular-nums`。

几何与密度：

- 表格、筛选条、详情分区圆角不超过 8px。
- 标签可使用胶囊形，但不能把每个指标都做成 Badge。
- 不使用渐变文字、玻璃拟态、排行榜奖牌、大面积渐变或彩色侧边条。
- 当前状态页的“分组卡片 + 模型卡片网格”适合少量分组，但不适合市场规模；市场上线时改为表格主视图，模型卡仅保留在详情或少量模型场景。

组件复用：

- `SectionPageLayout`：页面框架。
- `Tabs`：三类工作区切换。
- `Table` / TanStack Table：排序、列显隐、分页和行展开。
- `Input`、`Select`、`DropdownMenu`：搜索和筛选。
- `Badge`：仅用于状态和检测结论。
- `Tooltip`：解释 TTFT、Wilson 修正和检测新鲜度。
- `Dialog`：只用于危险确认和必要输入。
- `Skeleton`：表格加载；保持列宽不变。

### 14.13 响应式、动效与可访问性

响应式：

- 1440px 以上显示全部核心列，可选展示 TPS、独立消费者和趋势。
- 1024-1439px 隐藏 TPS、渠道主和更新时间，进入行展开区。
- 768-1023px 保留分组、状态、倍率、成功率、TTFT 和操作。
- 低于 768px 使用紧凑行，筛选进入底部 Sheet；不横向压缩完整桌面表格。

动效：

- Tabs、行展开、状态更新使用 150-220ms ease-out。
- 排名变化只在刷新后短暂高亮变化单元格，不移动整行制造干扰。
- 检测阶段变化使用图标与文本切换，不使用循环脉冲装饰。
- `prefers-reduced-motion` 下取消位移，仅保留即时状态或淡入。

可访问性：

- 表格排序按钮提供 `aria-sort`，筛选结果变化使用礼貌型 live region 播报。
- Tooltip 内容同时可通过键盘和触控访问，关键规则不能只藏在 Tooltip。
- 状态图标必须附文本；颜色不是唯一信息来源。
- 所有图标按钮提供可见 Tooltip 和无障碍名称。
- 焦点环使用现有 `ring` token，不能被表格滚动容器裁切。
- 对比度达到 WCAG 2.1 AA；弱化文本仍需满足正文可读性要求。

### 14.14 前端性能与数据请求策略

- 排行榜、市场列表全部服务端分页、筛选和排序，禁止一次加载全部分组。
- 搜索输入 250-350ms debounce，并取消过期请求。
- React Query Key 必须包含模型、时间窗、筛选、排序、页码和榜单版本。
- 榜单快照可缓存 30-60 秒；“我的渠道”状态轮询只在页面可见且存在进行中检测时启用。
- 趋势图按需加载，列表首屏不下载每一行的完整时序数据。
- 分组详情和检测报告使用路由级代码拆分。
- 表格行数固定为 20/50，不需要无限滚动；大量模型列表再考虑虚拟化。

## 17. 安全、隐私与风控

### 17.1 凭据安全

- 使用信封加密或外部 KMS/Vault；数据库只保存密文或引用。
- 密钥创建后不可回显，替换时生成新版本并撤销旧版本。
- 生产转发和检测读取凭据都记录审计，但审计不记录密钥内容。
- 管理员默认也不能查看明文；紧急访问需双人审批和独立审计。

### 17.2 SSRF 与网络隔离

- 解析并验证最终 IP，拒绝私网、环回、链路本地、保留地址和云元数据地址。
- 每次重定向重新校验目标，限制协议、端口和重定向次数。
- 检测 worker 与生产数据库、内部控制面网络隔离。
- 对 DNS 结果进行连接时校验，防止 DNS 重绑定。

### 17.3 权限与数据隔离

- 所有渠道主查询必须带 `owner_user_id` 条件，不能只依赖前端隐藏。
- 公开 API 使用专门 DTO，不返回内部渠道 ID、完整域名、密钥尾号以外信息或风险证据。
- 内部 Channel 增加市场来源和所有权元数据，但不把现有管理员写接口开放给用户。

### 17.4 结算风险

- 结算前校验请求、消费者、分组、倍率快照和账本预扣的一致性。
- 退款生成反向账本分录，不删除或修改原始结算。
- 渠道主账号受限时冻结待结算释放，已消费用户的退款仍优先处理。
- 现有支付密码锁定、失败次数和幂等规则继续用于可用收入转账。

## 19. 分阶段实施计划

### 阶段 0：许可与产品口径

- 确认第三方检测器商业授权；未取得授权时只启用自研检测器。
- 确认倍率上下限、结算观察期、榜单门槛和异常阈值。
- 固化 `marketplace_universal_only` 为用户上传分组唯一额度策略，只有 `official` 分组允许按模型使用 GPT 套餐和 GPT 专属额度。

### 阶段 1：领域与安全基础

- 新增市场渠道、分组、凭据、检测、结算和风险实体。
- 建立用户权限 API、密钥加密、SSRF 防护和审计。
- 创建内部 Channel 映射服务，不复用管理员 Handler。
- 增加迁移、唯一约束、幂等和并发测试。

### 阶段 2：检测与准入

- 实现 `ChannelDetector` 适配器和自研基础检测器。
- 建立检测 worker、任务限额、报告脱敏和过期机制。
- 实现管理员审核、暂停、恢复和证据查看。

### 阶段 3：通用额度计费与结算

- 在 Billing Session 引入 `credit_pool_policy`。
- 在路由后、预扣前生成不可变 `billing_policy_snapshot`，由预扣、结算、退款、重试和日志全链路复用。
- 用户上传分组强制通用额度预扣、结算、退款和使用日志标记；官方 GPT 分组保留 `subscription_gpt -> gpt_wallet`。
- 实现 5% 佣金、1% 手续费、94% 待结算和定时释放。
- 复用现有支付密码转账，但保留市场收入来源追踪。

### 阶段 4：分组市场与排行榜

- 扩展现有 `/group-status`，实现搜索、筛选、排序和分页。
- 扩展现有审计投影，加入分组级 TTFT、P50/P95 和独立消费者。
- 实现 Wilson 修正、cohort 归一化、榜单快照和防刷规则。
- 完成公开详情、渠道主工作台和管理员治理页。

### 阶段 5：灰度与上线

- 仅对测试渠道主开放，验证检测、转发、退款和结算全链路。
- 通过影子榜单验证排名稳定性，不立即对外展示名次。
- 小流量开放市场分组，设置平台总风险敞口与自动熔断。
- 连续完成账本对账、质量指标校验和安全审查后全量开放。

## 20. 验收标准

### 20.1 渠道与权限

- [ ] 普通用户只能管理自己创建的市场渠道，无法调用管理员渠道写接口。
- [ ] 每个新渠道由系统按倍率与 ID 生成独立分组名，用户无法自定义、覆盖或植入广告词。
- [ ] 倍率变更生成新路由版本，已开始请求使用旧版本完成，Token 绑定的稳定分组 ID 不变。
- [ ] 密钥创建后不回显，数据库、日志和检测报告均无明文密钥。
- [ ] Base URL 无法访问私网、环回或云元数据地址。
- [ ] 状态转换符合状态机，暂停或检测过期的分组不能接收新流量。

### 20.2 额度与账本

- [ ] 任意用户上传分组，无论声明 GPT、Codex、Responses 或其他允许模型，都只扣通用额度。
- [ ] 用户上传分组不查询、不预扣且不回退到 GPT 套餐或 GPT 专属额度。
- [ ] CodeGo 官方 GPT/Codex/Responses 按 `GPT 套餐 -> GPT 专属额度` 扣费，不扣通用额度。
- [ ] CodeGo 官方通用模型仍只扣通用额度，不能因为“官方”来源而跨池。
- [ ] 路由重试、内部渠道切换、退款和补偿始终使用请求创建时的额度策略快照。
- [ ] 将用户渠道映射到内部 Channel 或审核通过后，仍不能获得官方额度权限。
- [ ] 请求日志显示基础费用、倍率、应付、5% 佣金、1% 手续费和渠道主净收入。
- [ ] 成功结算后 94% 进入待结算，观察期结束后仅释放一次。
- [ ] 失败、退款、重试和重复回调不会重复扣款或重复发放收入。
- [ ] 渠道主不能通过消费自己的分组获得收入或榜单样本。

### 20.3 检测与排名

- [ ] GPT 渠道完成协议、流式、TTFT、错误率和模型可用性检测。
- [ ] 未取得商业授权时，构建产物和依赖中不包含 `gpt56_api_detector` 源码或其核心实现。
- [ ] 小样本分组显示“观测中”，不参与正式排名。
- [ ] 榜单使用固定版本的 Wilson 修正、指标归一化和惩罚规则。
- [ ] 搜索、筛选、排序和分页组合查询结果稳定且可复现。
- [ ] 排名表的成功率、TTFT、延迟和请求量与审计原始数据抽样一致。

### 20.4 前端体验

- [ ] 桌面和移动端均无横向溢出、文字遮挡或无限列表堆叠。
- [ ] 列表、详情、Token 绑定确认和使用日志均明确显示“CodeGo 官方/用户渠道”与实际额度池。
- [ ] 分组选择器按“CodeGo 官方”和“用户渠道”分区，搜索后仍保留来源标签和额度规则。
- [ ] 加载、空、错误、检测中、降级、暂停和无权限状态完整。
- [ ] 键盘可完成搜索、筛选、排序、分页和展开详情。
- [ ] 状态不只依赖颜色，焦点可见，关键文本满足 WCAG 2.1 AA 对比度。
- [ ] 开启减弱动效时不播放非必要动画。

## 21. 风险与待确认事项

| 风险/决策 | 当前建议 | 影响 |
|---|---|---|
| 第三方检测器商业许可 | 先取得书面授权，否则只做自研兼容检测 | 未授权不能直接合入用户指定项目 |
| 用户上传分组只使用通用额度 | 通过 `source_type=marketplace_user` + `marketplace_universal_only` 强制隔离 | 需要路由、Billing Session、API、日志和账本保存策略快照 |
| 系统分组命名 | 倍率 + 不可猜 ID，用户无命名权限 | 防止广告、冒充官方和路由名称冲突 |
| 平台是否承担上游成本 | 渠道主承担其上游成本，平台只结算平台额度 | 必须在渠道主协议中写清楚 |
| 倍率范围 | 建议 0.50x-3.00x，异常值人工审核 | 影响竞争、套利和用户预期 |
| 待结算周期 | 建议 24 小时，可按风险等级延长 | 影响渠道主资金流动性和退款能力 |
| 排名最低样本 | 24h 100 请求/10 用户起榜 | 需结合真实流量灰度调整 |
| 分组与渠道关系 | 首期一对一，模型保留一对多能力 | 降低首期路由和归因复杂度 |
| 公开渠道主信息 | 只显示公开昵称，不展示用户 ID 或真实身份 | 降低骚扰和隐私风险 |

## 22. 最终建议

首期应把“安全创建渠道、可靠检测、通用额度结算、可解释排名”作为一个完整闭环交付，不应先上线无检测的公开渠道，也不应把现有管理员渠道表直接暴露给用户。

实现优先级建议为：

```text
独立市场领域与密钥安全
  -> 自研检测适配器与审核
  -> 通用额度扣费和不可变结算
  -> 搜索分页与公开状态
  -> 影子排行榜
  -> 正式公开排名
```

其中，第三方检测器的商业授权是外部阻塞项；其余架构和基础检测可以在不等待授权的情况下按本方案推进。

## 23. 二次分析：当前方案还缺少什么

### 23.1 当前代码能力与差距

| 当前能力 | 已有基础 | 仍需增加 |
|---|---|---|
| 分组状态 | `/api/user/self/group-status`、24h 状态序列、模型请求量 | 市场所有权、倍率、检测新鲜度、分页搜索和公开状态 |
| 分组概览 | 成功率、平均延迟、TPS、请求量、模型数 | TTFT 聚合、P50/P95、独立消费者、榜单快照和置信修正 |
| 分组选择 | User 和 Token 均有 Group 字段，Token 支持跨组重试 | 市场分组 Token 绑定、跨池回退禁止、选择审计和失效提示 |
| 渠道管理 | 管理员渠道 CRUD、测试、模型获取 | 用户所有权、凭据保险库、审核映射、渠道主权限 API |
| 使用日志 | 分组倍率、扣费来源、计算公式详情 | 市场标识、渠道主收益拆分、通用额度例外策略和结算关联 ID |
| 账本与转账 | 不可变账本、预扣/结算/退款、支付密码转账 | 渠道主待结算账户、平台收入账户、释放任务和风险冻结 |
| 前端状态页 | 少量分组的卡片网格 | 面向大量分组的表格、Tabs、筛选、详情、创建与治理流程 |

### 23.2 必须新增的 P0 能力

1. **不可伪造的分组来源**：服务端持久化 `official` 与 `marketplace_user`，禁止前端传入、名称推断或普通接口修改。
2. **额度策略快照**：路由后、预扣前锁定来源和额度池，预扣、结算、退款、重试、日志使用同一版本快照。
3. **系统分组命名**：按倍率与不可猜 ID 生成展示名和内部名，倍率变更通过路由版本排空切换。
4. **Token 级分组绑定**：明确选择分组影响哪个 Token，禁止直接修改用户全局分组。
5. **回退边界**：用户上传分组故障时不得回退到官方分组；同池自动回退需用户明确开启。
6. **渠道容量模型**：保存最大并发、QPS、维护窗口和实时容量利用率，否则高排名会把渠道瞬间压垮。
7. **价格变更治理**：倍率变更延迟生效、限制频率并保留价格历史，防止低价引流后立即涨价。
8. **上游授权声明**：渠道主必须确认拥有转售/共享调用权限，平台保留要求证明和下架的权利。
9. **请求内容隔离**：渠道主只能看聚合指标和脱敏错误，不能看到消费者 Prompt、Response、Token 名称或身份。
10. **结算风险准备金**：待结算余额需要风险冻结、退款优先级和负余额处理规则。
11. **冷启动机制**：新分组需要“观测中”曝光和可选探索流量，否则没有样本就永远无法进入榜单。
12. **删除前置条件**：未结算、争议中、检测中或仍有 Token 绑定时不能删除分组。
13. **协议版本兼容**：检测结果必须区分 Chat Completions、Responses、Codex Native 和工具调用能力，不能只给一个总通过状态。

### 23.3 建议新增的 P1 能力

- 最多 3 个分组并排比较。
- 分组收藏和最近使用。
- 渠道主维护公告与计划维护窗口。
- 检测结果即将过期提醒、密钥失效提醒和收入释放通知。
- 渠道主质量周报：成功率、延迟、流失消费者和排名变化。
- 管理员可配置榜单门槛、评分权重、风险阈值和倍率上下限。
- 模型别名规范化，避免同一模型用多个别名分散排名样本。
- 消费者对请求质量发起争议，但不能直接评价模型身份或公开敏感错误。

### 23.4 可延后的 P2 能力

- 公开未登录榜单。
- 市场自动分组和同池自动切换。
- 多渠道组成一个渠道主分组。
- 渠道主品牌主页、关注和订阅更新。
- API 形式的榜单快照导出。
- 更复杂的信誉等级或服务等级协议。

## 24. 关键用户故事

### 24.1 消费者选择分组

**用户故事**：作为 API 消费者，我希望按模型、成功率、TTFT 和倍率筛选市场分组，并将确认后的分组绑定到指定 Token，从而在不影响其他项目的情况下使用该渠道。

验收条件：

- 用户能看到分组状态、倍率、检测时间、样本量和费用示例。
- 用户必须选择已有 Token 或新建 Token，不能默认修改全部 Token。
- 确认前明确说明分组来源、实际额度池及失败回退规则；用户渠道固定说明只消耗通用额度。
- 绑定完成后，Token 列表和使用日志都能显示市场分组。

### 24.2 渠道主发布渠道

**用户故事**：作为渠道主，我希望安全提交连接信息、声明模型与容量、设置倍率并完成检测，从而把渠道发布为独立分组。

验收条件：

- API Key 提交后不回显且不进入普通草稿。
- 检测阶段、请求数量和失败原因清晰可见。
- 发布前显示消费者价格、平台费用和渠道主净收入示例。
- 未通过检测或审核时不能接收真实消费者流量。

### 24.3 渠道主运营与结算

**用户故事**：作为渠道主，我希望看到质量、容量、收入和待结算状态，并能安全轮换密钥或暂停服务，从而控制服务风险。

验收条件：

- 可查看模型级成功率、TTFT、错误率和容量利用率。
- 替换密钥失败不会破坏当前可用密钥。
- 暂停后不接收新请求，已有请求按原快照结算。
- 每笔收入能关联请求结算、平台费用和预计释放时间。

### 24.4 管理员治理

**用户故事**：作为管理员，我希望按风险和待处理状态查看渠道，并基于检测、关联关系和账本证据做出审核或暂停决定。

验收条件：

- 管理员操作必须填写原因并产生审计记录。
- 暂停前显示受影响 Token 数、进行中请求和待结算金额。
- 管理员不能查看 API Key 明文或消费者 Prompt/Response。
- 恢复服务需要检测仍有效或重新检测通过。

## 25. 成功指标与反向指标

### 25.1 北极星指标

**每周由健康市场分组成功完成并结算的请求数**。

该指标同时要求真实消费、请求成功、渠道市场被采用和账本完成结算，比单纯分组数量或 GMV 更能代表市场价值。

### 25.2 上线后三个月建议目标

| 维度 | 指标 | 建议目标 |
|---|---|---:|
| 供给激活 | 提交渠道中 7 天内完成检测并发布 | >= 60% |
| 消费激活 | 查看详情后成功绑定 Token | >= 25% |
| 质量 | 市场请求成功率 | >= 97% |
| 性能 | 市场列表 API P95 | < 500ms |
| 任务成功 | 创建渠道流程完成率 | >= 70% |
| 结算 | 到期收入按时释放率 | >= 99.9% |
| 争议 | 市场请求退款/争议率 | < 1% |
| 留存 | 首次使用市场分组后 4 周仍有请求的用户 | >= 35% |

### 25.3 反向指标

- 平台总退款和补偿不得超过市场 GMV 的既定风险预算。
- 不能因低价排名导致成功率或 P95 延迟持续恶化。
- 渠道主集中度需要监控，单一渠道主不应长期占据绝大多数市场流量。
- 市场增长不能提高错误扣池、账本不一致或密钥泄露事件。
- 6% 平台费率需要覆盖检测、账本、风控、客服和退款损失；若单位贡献为负，应调整最低手续费、风险准备金或费率，而不是依赖规模弥补。

## 26. 实施前必须确认的产品决策

| 决策 | 推荐默认值 | 未确认风险 |
|---|---|---|
| 分组生效范围 | Token 级绑定 | 全局切换会影响用户所有线上项目 |
| 分组来源与额度 | 用户渠道仅通用额度；CodeGo 官方 GPT 才可用 GPT 套餐/GPT 专属额度 | 来源可伪造或策略未锁定会导致跨池扣费 |
| 用户分组命名 | 系统按倍率 + ID 生成 | 自定义名称会产生广告、冒充和审核成本 |
| 市场故障回退 | 默认不跨分组回退 | 静默回退可能改变渠道主和额度池 |
| 倍率生效延迟 | 1 小时，24 小时最多修改 1 次 | 可能出现低价引流后即时涨价 |
| 容量声明 | 最大并发 + QPS + 维护窗口 | 排名流量可能压垮小渠道 |
| 冷启动曝光 | 观测中专区 + 有上限的探索曝光 | 新分组无法获得真实样本 |
| 待结算与准备金 | 24 小时，风险事件可延长 | 欺诈或退款时余额已被转走 |
| 删除条件 | 无绑定、无请求、无争议、无待结算 | 删除后无法完成退款和审计 |
| 数据可见性 | 渠道主仅看聚合与脱敏错误 | Prompt、Response 和用户身份泄露 |
| 排名更新周期 | 5-15 分钟生成快照 | 实时排名容易抖动和被操纵 |
| 管理员审核 | 首次发布和关键配置变更必须审核 | 恶意渠道可绕过首次准入 |

在这些决策未冻结前，不建议直接开始前后端并行开发；否则 Token 绑定、扣费、回退和结算接口会反复改动。
