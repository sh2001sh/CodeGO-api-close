# 平台托管式渠道市场方案

## 结论

产品不采用开放式论坛和用户私聊，而采用“平台托管工单 + 受控渠道公告页”。渠道主可以在平台内推广服务、处理售后和发布更新，但渠道主与用户之间不建立直接联系，所有沟通、审核、扣费和结算都经过平台。

目标是把售后群从广告和售后混杂的沟通场所，转变为辅助通知渠道；主要推广、售后、评价和争议处理迁移到网站，并保留平台对私下交易和刷量的控制能力。

## 产品边界

### 允许

- 渠道主发布经过审核的渠道公告、模型更新、维护通知、降倍率通知和使用说明。
- 用户查看渠道主页、模型价格、实时状态、检测报告、公告和用户评价。
- 用户从渠道、模型、请求记录或扣费记录提交售后工单。
- 渠道主在工单内提交处理结果。
- 平台审核用户问题和渠道主反馈后再展示给对方。
- 用户收藏、关注渠道和举报公告。

### 禁止

- 用户与渠道主私聊。
- 公布微信、QQ、Telegram、Discord、邮箱、手机号、二维码、外部群和外部收款地址。
- 渠道主通过平台向用户直接出售 Key、额度或服务。
- 渠道主删除真实负面评价、修改平台统计或引导用户离开平台。
- 自己给自己的渠道点赞、收藏、评价、提问、举报、申请砍价或制造互动数据。

## 工单流程

```text
用户草稿
→ 待平台审核
→ 待渠道处理
→ 渠道已回复
→ 待平台审核反馈
→ 待用户确认
→ 已解决
```

异常状态包括：用户补充材料、平台介入、渠道超时、反馈被退回、争议中和已关闭。

### 用户提交

用户从渠道详情、请求记录或扣费记录提交工单。系统自动关联：

- 渠道 ID、分组 ID和模型
- 请求 ID、请求时间和请求状态
- 扣费金额和错误信息

工单内容需要过滤联系方式、外链、二维码和私下交易引导。工单创建者只看到自己的工单，渠道主只看到脱敏用户编号和必要的请求信息。

### 平台初审

自动通过条件：工单绑定真实请求、请求记录有效、内容无联系方式且属于标准售后类型。

人工审核条件：扣费争议、退款要求、无关联请求、联系方式疑似内容、重复投诉、互相举报和高风险渠道投诉。

### 渠道主处理

渠道主只能选择标准处理结果：已修复、已确认问题、正在维护、不支持该模型、需要更多信息或驳回并说明理由。渠道主不能主动联系用户，不能删除原始问题，不能承诺平台外退款。

### 反馈复审

渠道主提交的反馈先进入“待平台审核”。平台检查是否回应问题、是否与请求日志矛盾、是否存在导流信息和不当承诺。通过后才展示给用户；不通过则退回修改，严重情况由平台代处理。

### 用户确认与平台介入

用户可以确认解决、补充材料或申请平台介入。渠道主超过 SLA 未处理时自动提醒并升级平台；多次超时会影响信用分，必要时暂停渠道。

## 渠道公告页

公告页不是开放论坛，命名为“渠道公告”或“服务动态”。每篇内容必须关联一个渠道，并包含标题、正文、可选图片、关联模型、有效时间和置顶状态。

允许内容：新增模型、兼容性说明、降倍率、维护、恢复、性能说明、使用教程、活动规则和常见问题。

禁止内容：联系方式、二维码、外部群、外部收款、私下优惠、私下卖 Key、引导加好友、虚假成功率、虚假延迟和未经平台确认的承诺。

公告需要经过平台审核后展示；每天每个渠道默认最多发布 3 条，每周最多置顶 1 条，同类内容不能重复发布。公告互动只提供收藏、关注、帮助反馈、举报和“针对公告提交工单”，不提供自由评论、@用户或私信。

## 反导流和反作弊

### 内容审核

文本审核检测联系方式、外链、收款信息和导流措辞；图片上传执行 OCR 检测二维码、账号和手机号。违规内容不展示，首次要求修改，重复违规降低曝光，严重违规暂停渠道。

### 身份和互动隔离

渠道主不能对自己的渠道点赞、收藏、评价、提问、回复自己的问题或制造互动数据。渠道主及关联账号的请求可以正常服务，但不计入公开成功率、热门排序、推荐权重和评价资格。

### 异常流量

识别同 IP、设备、Cookie、支付账户、规律间隔、单一模型和低额度高频请求等异常组合。异常流量进入观察状态，不直接改变公开排名；平台保留复核和申诉入口。

### 评价规则

评价必须绑定真实成功请求，并满足最小请求次数和评价时间窗口。同一用户同一渠道限制评价频率。渠道主可以回复但不能删除真实评价；平台可以折叠违规内容并保留审计记录。

## 推荐和信用

渠道主发布内容数量不直接提高排名。推荐排序综合真实用户数、真实请求成功率、延迟、售后响应速度、投诉率、评价可信度、稳定运行时间和违规记录。

渠道信用分由工单按时处理率、用户确认解决率、反馈退回次数、投诉成立率、联系方式违规次数、异常流量比例和公告审核通过率组成，影响公告审核方式、展示位置、推荐曝光和批量发布权限。

## 分阶段实施

### 第一阶段：工单闭环

1. 建立工单、工单消息和状态流转表。
2. 从请求记录创建工单并自动关联请求上下文。
3. 增加平台初审、渠道主处理、反馈复审和用户确认。
4. 增加渠道超时、平台介入和站内通知。
5. 增加联系方式和外链文本过滤。

验收：用户能从真实请求提交工单；渠道主看不到联系方式；渠道反馈未经审核不会展示；超时可升级平台。

### 第二阶段：受控渠道公告

1. 增加渠道公告编辑、草稿、审核、发布和到期状态。
2. 增加渠道主页公告区、市场公告流和关注通知。
3. 增加图片上传和 OCR 导流检测。
4. 增加发布频率、置顶频率和重复内容限制。

验收：公告经过审核才能展示；违规联系方式不能发布；用户可以从公告进入工单但不能私聊。

### 第三阶段：评价和信任体系

1. 将评价资格绑定真实请求。
2. 排除渠道主和关联账号的自用流量。
3. 增加异常互动、刷量和关联账号风控。
4. 建立渠道信用分和违规记录。

验收：渠道主无法给自己刷评价或热度；异常流量不影响公开排名；投诉和违规可追溯。

### 第四阶段：平台推荐和仲裁

1. 建立稳定、性价比、售后响应等榜单。
2. 提供官方推荐位和认证标识。
3. 建立争议仲裁、申诉和证据留存。
4. 根据信用分调整审核和曝光策略。

## 实施原则

- 所有用户和渠道主沟通都绑定渠道、请求、扣费、评价或工单上下文。
- 平台统计数据只能由系统生成，渠道主内容只作为说明，不覆盖统计。
- 权限校验放在后端，不能依赖前端隐藏按钮。
- 站内交易、扣费和结算保持平台托管，公告页不提供外部成交入口。
- 先完成工单闭环，再做公告和推荐，不先建设自由社区。
